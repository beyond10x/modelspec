**Initial execution target:** NVIDIA RTX 3090 via Vulkan compute / SPIR-V  
**Principle:** Specify *what* to compute; the compiler determines *how* to execute it.

## 0. Executive decision

ModelSpec is a versioned, declarative language and compiler for specifying differentiable tensor programs. A model is built compositionally from scalar functions, tensor operations, reusable modules, and architectures. A training specification adds a loss, optimizer, data bindings, and execution policy. The compiler elaborates the entire training step, generates its gradient computation, optimizes the resulting graph, schedules GPU kernels, and runs them in an independently owned Rust runtime.

The initial stack has **no Python, PyTorch, or CUDA API/toolkit dependency**. It uses the system Vulkan loader and an installed NVIDIA Vulkan driver, which translates the emitted SPIR-V into GPU-native instructions. This is **not** direct generation of NVIDIA SASS or an attempt to replace the NVIDIA kernel-mode driver.

We optimize for correctness and coherent architecture before raw speed. Near-optimal performance on a wide range of neural networks is a long-term research and engineering goal, **not** a v1 guarantee.

### Non-negotiable invariants

1. **One semantic core.** CPU reference execution and GPU compilation consume the same verified tensor IR.
2. **Composition does not mandate kernel boundaries.** Functions/layers are inlined or lowered; operations may fuse or split.
3. **Shapes and dtypes are explicit.** The compiler rejects invalid operations before dispatch.
4. **Purity by default.** Parameters, random state, and optimizer updates have explicit identities/effects; graph rewrites cannot silently change them.
5. **Training is compiled.** Forward, loss, backward, and optimizer are part of a single optimizable `train_step` program.
6. **Hardware features are queried.** No assumptions that a particular Vulkan extension, dtype, or cooperative matrix shape is supported by the driver's current configuration.
7. **Testable at every lowering stage.** Introspection, differential testing, and profiling are design requirements.

## 2. ModelSpec source language

Source files end in `.mspec`. The language is *declarative, statically typed, pure by default*, with generic dimension parameters and explicit state declarations. Modules are reusable units. `forward` is a regular pure function, not a magical runtime hook.

```modelspec
module Linear<In: dim, Out: dim> {
    param weight: Tensor<f32, [In, Out]> = xavier_uniform();

    fn forward<B: dim>(x: Tensor<f32, [B, In]>)
        -> Tensor<f32, [B, Out]> {
        return matmul(x, weight);
    }
}

model TinyMLP<B: dim> {
    layer fc1: Linear<32, 64>;
    layer fc2: Linear<64, 1>;

    fn forward(x: Tensor<f32, [B, 32]>)
        -> Tensor<f32, [B, 1]> {
        let h = relu(fc1.forward(x));
        return fc2.forward(h);
    }
}

train TinyFit {
    model = TinyMLP<64>;
    input  x: Tensor<f32, [64, 32]>;
    target y: Tensor<f32, [64, 1]>;
    loss = mse(model.forward(x), y);
    optimizer = sgd(lr = 0.001);
    steps = 1000;
    seed = 42;
    device = vulkan(0);
}
```

This is the **target language design**, not a claim that a parser already exists. M0 can start with a restricted subset: one model, static dimensions, `f32`, parameters, local `let`, `matmul`, `add`, `sub`, `mul`, `relu`, `mean`, `mse`, and SGD. Introduce modules and generics through compile-time elaboration without changing core tensor semantics.

### 2.1 Surface constructs

| Construct | Meaning | Lowering |
| --- | --- | --- |
| `fn` | Pure, typed mathematical function | Inline or call graph specialization |
| `module` | Reusable collection of params/functions | Instance elaboration with stable names |
| `layer` | Named module instance | Statically instantiate; no runtime object |
| `model` | Parameterized architecture | Closed graph from entry-point functions |
| `param` | Persistent named trainable tensor | Parameter handle + initialization spec |
| `const` | Immutable scalar or tensor | Constant IR value |
| `train` | Loss, optimizer, dataset interface, execution policy | Stateful training-step IR |
| `infer` (later) | Inference signature and export policy | Read-only compiled execution graph |
| `target` (later) | Optional capabilities/optimization constraints | Backend configuration, not model semantics |

The loss of a `train` block calls `model.forward` exactly once, counting calls nested in its arguments; the checker refuses zero calls at the loss and a second call at that call (E-TYPE-017).

An operator call takes its operands as positional arguments, and after them the operator's named compile-time arguments, `name = <literal>`, in any order among themselves. `heads = <integer literal>` of `attention` is the first; the operator registry lists each operator's named parameters and their kind (`ops::named_parameters`), so a later operator such as `dropout` reuses the same check. Every named argument is required and given once: one the call omits is E-TYPE-001 at the call, one the operator does not take, one given twice or one before an operand (named arguments follow the operands) is E-TYPE-002 at the argument, and a value that is not a literal of the parameter's kind (for `heads` an integer literal of at least 1, so not a name, an expression, `0` or `2.0`) is E-TYPE-019 at the argument. The value is part of the Tensor IR op (`Attention { heads }`), so it fixes the shapes the checker and the verifier see. A named argument to an operator that takes none, or to a model function, stays E-TYPE-002.

The `optimizer` setting of a `train` block is `sgd(lr = F)` or `adamw(lr = F, weight_decay = F, beta1 = F, beta2 = F, eps = F, warmup_steps = N)`. `sgd` takes `lr` alone and keeps it constant; an argument after it is E-SYNTAX-002 at the comma before it, naming the argument. `adamw` takes all six arguments, each once and named, in any order, `warmup_steps` an integer literal and the others float literals: one it omits is E-TYPE-001 at the `adamw` call, an unnamed, unknown or repeated one E-TYPE-002 and a value of the other kind E-TYPE-019 at the argument. Its `lr` is a positive finite `f32` like `sgd`'s (E-TYPE-010); `weight_decay` below 0, `beta1` or `beta2` outside [0, 1) once rounded to `f32` and `eps` not above 0 are E-TYPE-023, and `warmup_steps` not below `steps` is E-TYPE-024, each at the argument. At step `t`, counted from 1, every parameter `p` with a gradient `g` takes `m = beta1 * m + (1 - beta1) * g`, `v = beta2 * v + (1 - beta2) * g * g` and `p = p - lr_t * (m * c1 / (sqrt(v * c2) + eps) + weight_decay * p)` (Loshchilov and Hutter, decoupled weight decay, applied to every parameter: the language has no parameter groups). Each elementwise operation is one rounded `f32` operation in that written order, left to right, and none is fused into a multiply-add, so the fused chains of § 3.1 and a later Vulkan kernel can write the same bits. The CPU reference is measured that way: its parameters and moments are bit-equal to an `f32` reference that rounds every operation in this written order from the host constants below, not within a relative bound of an `f64` update, which cancellation in `p - lr_t * (...)` does not allow (coordinator decision D64). The learning rate rises linearly from 0 and falls linearly to 0 at the last step of the run: `lr_t = lr * t / warmup_steps` for `t <= warmup_steps` and `lr * (steps - t) / (steps - warmup_steps)` after, `steps` the run's total, as in BERT pre-training (Devlin et al. 2019); `warmup_steps = 0` has no warmup, and a `train --steps` that leaves `warmup_steps` not below the run's steps stops the run before its first step, exit 1 (coordinator decision D50, settlement 1). The whole update is Tensor IR, the step's `Optimizer` subgraph; `Sqrt` and `Div` are internal elementwise ops of that subgraph, never source operators.

The third optimizer is `muon(lr = F, momentum = F, weight_decay = F, ns_steps = N, warmup_steps = N, adam_lr = F, beta1 = F, beta2 = F, eps = F)`. It takes all nine arguments under the rules of `adamw`: each once and named, in any order, `ns_steps` and `warmup_steps` integer literals and the others float literals, with E-TYPE-001, E-TYPE-002 and E-TYPE-019 as for `adamw`. `lr` and `adam_lr` are positive finite `f32` values (E-TYPE-010), `weight_decay`, `beta1`, `beta2` and `eps` are held to the ranges of `adamw` (E-TYPE-023) and `warmup_steps` must be below `steps` (E-TYPE-024). A `momentum` outside [0, 1) once rounded to `f32`, or an `ns_steps` outside [1, 10], is E-TYPE-025 at the argument. The compiler splits the parameters once: a parameter with a gradient, a static shape of rank 2 and a value that no `embedding` reads as its table (by dataflow, through `let`s and model functions) takes Muon. Every other parameter takes AdamW with `adam_lr` as its `lr`, and the `beta1`, `beta2`, `eps`, `weight_decay`, moments and schedule of `adamw`. That covers a bias, a `layer_norm` gain and an embedding table, tied into the output projection or not. A Muon parameter `p` of shape `[rows, cols]` with gradient `g` and momentum buffer `b` takes, at step `t`: `b = momentum * b + g`; the Nesterov step `u = g + momentum * b`; `x = u / (sqrt(sum(u * u)) + 1e-7)`; then `ns_steps` quintic Newton–Schulz steps `A = x xᵀ`, `x = 3.4445 x + (-4.7750 A + 2.0315 A A) x`; and `p = p - lr_t * (s * x + weight_decay * p)`, with `s = 0.2 * sqrt(max(rows, cols))` computed in `f64` and rounded once to `f32` (Jordan et al. 2024; Liu et al. 2025, whose scale matches the update RMS of AdamW). When `rows > cols`, `x` is transposed before the Newton–Schulz steps and back after them, so `A` is always the smaller Gram matrix, as in `torch.optim.Muon`. Each operation is one rounded `f32` operation in that written order, and the matmuls run in the order of § 2.2. The CPU reference is bit-equal to an `f32` reference that rounds in the same order. `lr_t` follows the schedule of `adamw` from `lr`, and the AdamW parameters take the same schedule from `adam_lr`. A run reports the Muon rate as its learning rate when a parameter takes Muon, else the `adam_lr` rate, so the rate it reports is one a parameter applies (coordinator decision D69). The quintic does not converge to 1. Its fixed band is about [0.68, 1.20] (local maximum f(0.5545) = 1.2024, local minimum f(1.050) = 0.6819). After 5 steps a Gaussian `[64, 32]` momentum has singular values in [0.6819, 1.1293] and an update RMS of 0.1762, not 0.2 (`crates/modelspec-runtime/tests/muon.rs`, `newton_schulz_singular_values`); `torch.optim.Muon` in `f32` gives the same band. On the masked-language-model fixture `mlm_dense.mspec` over the packed test corpus, a 300-step run at `lr = adam_lr = 0.01`, `momentum = 0.95`, `ns_steps = 5` and `warmup_steps = 30` reaches a held-out loss at step 300 of 6.7210197 under Muon and 6.724814 under AdamW at the same `lr` (`crates/modelspec-cli/tests/train_muon.rs`). Across seeds 1 to 10 Muon's held-out loss at step 300 is lower in 9 and higher at seed 2 (5.9449 against 5.9250), so the comparison on this corpus is within seed noise; the story's acceptance 5 is recorded as met at its seed and as within noise across seeds (`crates/modelspec-cli/tests/adversary_muon_cli.rs`, coordinator decision D69). The PyTorch opponent `opponents/bert_tiny` gives 6.6212 and 6.7239 for the same comparison. Both curves rise from about ln 300 after step 0, because 300 steps overfit the 26-sequence corpus. So the comparison shows that Muon is not worse than AdamW here, not that it is better (coordinator decision D67).

### 2.2 Type system and shapes

Canonical tensor type: `Tensor<dtype, [shape...]>`, where each dimension is a positive compile-time integer or a generic dimension that must be resolved for M0/M1 compilation. Rank 0 means scalar. `f32` is the only guaranteed M0/M1 numeric dtype. Later add `f16`, signed integers, boolean masks, and quantized formats behind verified device capabilities.

`i32` is the one other dtype, and it holds row ids and class labels only. An `i32` tensor is declared by an `input` or `target` of a train block or by a function parameter, and the only operands that read one are the ids of `embedding` and the labels of `cross_entropy`. The checker refuses every other use with E-TYPE-018: an `i32` operand of any other operator (or as the table of `embedding`, or as the logits or weights of `cross_entropy`), an `f32` operand where those ids or labels go, a `param` of type `i32`, and a function declared to return `i32`. Parameters, program outputs and checkpoint tensors stay `f32`, and the verifier holds the Tensor IR to the same rule. Synthetic data cannot supply an `i32` input or target, so `train` refuses one with E-DATA-004; a dense `--data` directory supplies it from `<name>.i32`, each value checked before the first step against the rows or classes that read it (E-DATA-011), and a packed one binds `ids`, `positions` and `labels` (§ 8, § 8.1).

M0/M1 shape rules, intentionally strict:

- `matmul([M,K], [K,N]) -> [M,N]` for rank-2 tensors; mismatches are compile errors.
- `add`, `sub`, `mul`: same-shape inputs, or a scalar and tensor; **no implicit non-scalar broadcasting yet**.
- `relu([*S]) -> [*S]`; `transpose([M,N]) -> [N,M]`.
- `sum([*S]) -> []`, `mean([*S]) -> []` with an explicit specified reduction order policy.
- `mse(a, b) -> []` iff `a` and `b` have identical shapes; defined as `sum((a-b)^2) / element_count(a)`.
- `embedding(table: f32[V,H], ids: i32[N]) -> f32[N,H]`: row `n` of the result is row `ids[n]` of the table. A positional embedding is the same operator over a second table and a positions input, `embedding(pos, positions)`. An id outside `0..V` is a runtime error of the CPU interpreter, checked before the first node runs, not a panic.
- `add_rows(x: f32[N,H], b: f32[H]) -> f32[N,H]`: `b` added to every row of `x`, the bias of a dense layer `add_rows(matmul(x, w), b)`. It is the one row broadcast, named and explicit; `add` keeps the same-shape-or-scalar rule. A `b` of another length is E-TYPE-003 and an `x` not of rank 2 or a `b` not of rank 1 is E-TYPE-004, at the call.
- `gelu([*S]) -> [*S]`: the tanh form of GELU, element by element (§ 4).
- `layer_norm(x: f32[N,H], gamma: f32[H], beta: f32[H]) -> f32[N,H]`: each row of `x` less its mean, divided by `sqrt(var + 1e-12)` with `var` the row's biased variance, times `gamma` plus `beta` (§ 4). `eps` and the axis are fixed. A `gamma` or `beta` of another length is E-TYPE-003 and an `x` not of rank 2 or a `gamma` or `beta` not of rank 1 is E-TYPE-004, at the call.
- `softmax(x: f32[N,K]) -> f32[N,K]`: per row `exp(x - max) / sum(exp(x - max))` (§ 4). The axis is the last; an `x` not of rank 2 is E-TYPE-004 at the call.
- `attention(q: f32[N,H], k: f32[N,H], v: f32[N,H], key_mask: f32[B,S], heads = A) -> f32[N,H]` with `N = B * S`: rows `b * S` to `b * S + S - 1` are sequence `b`, head `a` reads columns `a * H/A` to `(a + 1) * H/A - 1`, and each query attends to the keys of its own sequence whose mask entry is 1 (§ 4). A `k` or `v` of another shape than `q`, or a `key_mask` whose `B * S` is not `N`, is E-TYPE-003; an operand not of rank 2 is E-TYPE-004; `heads` that does not divide `H` is E-TYPE-020; all at the call. The key mask takes no gradient, so one whose value reads a `param` by dataflow is E-TYPE-021 (coordinator decision D41): directly, through a `let` or an operator, through a model function call whose result reads one, or through an argument of a model function call that reaches the key mask inside the function. It is reported at the key mask argument, or at the call's argument in the last case; training needs a gradient for every parameter the loss reads. A model function that reads no parameter, or whose parameter-reading argument does not reach its result, is no reason to refuse. A mask value other than 0 or 1 (NaN included), or a sequence with no key of value 1, is a runtime error of the CPU interpreter naming the sequence, checked before the op runs, not NaN.
- `cross_entropy(logits: f32[N,V], labels: i32[N], weights: f32[N]) -> f32[]`: `sum_n weights[n] * loss_n / sum_n weights[n]`, `loss_n` the log-sum-exp of row `n` of `logits` less `logits[n, labels[n]]` (§ 4, coordinator decision D43). It is the masked-language-model loss: a row the batch does not select has weight 0, and the tied decoder of BERT is `matmul(embedding(table, ids), transpose(table))`, the one table read twice. `labels` or `weights` of another length than `N` is E-TYPE-003, `logits` not of rank 2 or `labels` or `weights` not of rank 1 is E-TYPE-004, `f32` labels are E-TYPE-018, all at the call. `labels` and `weights` take no gradient, so either one reading a `param` by dataflow is E-TYPE-021 by the rule of the key mask of `attention`, at the argument. A label outside `0..V`, or a weight that is negative (`-0.0` is not) or not finite, is a runtime error of the CPU interpreter naming the row, checked in ascending row order, the label of a row before its weight, before the op's arithmetic; a weight sum of 0 is not an error (§ 4).
- `stop_gradient([*S]) -> [*S]`: its `f32` operand unchanged, of any shape; an `i32` operand is E-TYPE-018. No gradient flows back through it (§ 4), so a target branch such as `stop_gradient(matmul(x, w))` is held constant within a step. It is a source operator of the Tensor IR (`StopGradient`), and a pass after autodiff replaces each use by its operand, so neither the CPU interpreter nor the Vulkan scheduler sees it. A parameter that reaches the loss only through `stop_gradient` would get no gradient, and is E-TYPE-026 at the call (§ 8.1).
- `sigreg(z: f32[N,K], slices = M) -> f32[]`: the sketched isotropic Gaussian regularizer of LeJEPA (Balestriero and LeCun, arXiv 2511.08544, § 4.2), the Epps–Pulley statistic of each of `M` random unit directions averaged over the directions: `mean_m T_m` over the columns of `P = z @ proj`, `proj: f32[K,M]` the projection of the call's site at the step (§ 2.3, § 4). It lowers to `reduce_mean(SigregColumns(matmul(z, proj)))`; `proj` is an internal input that no source value supplies. `slices` is a required integer literal of at least 1. A `z` not of rank 2 is E-TYPE-004 and an `i32` `z` E-TYPE-018, at the call; `slices = 0` is E-TYPE-019 at the argument, and a `slices` that makes the projection `f32[K,M]`, `P: f32[N,M]` or the columns `f32[M]` overflow `u64` in its element or byte count is E-TYPE-016 at the argument, as every count overflow is a hard error. On the Vulkan backend `SigregColumns` and `SigregColumnsGrad` are per-column kernels (§ 5.2) and `train --backend vulkan` uploads each site's projection before each step (§ 8); `infer --backend vulkan` answers E-TARGET-011 at the call, because inference runs the loss steps once with no step to draw the projection for.
- Reduction order policy (the CPU reference, § 9 gate 2): a sum accumulates sequentially in row-major index order in the element type, starting from its first term, with every product, difference and partial sum rounded to the element type (no fused multiply-add); `matmul` accumulates each output element over the contracting index in ascending order the same way; `mean` is that sum divided by the element count converted to the element type; `mse` is that sum of `(a-b)^2` divided by the element count converted to the element type.
- Reduction order policy (the CPU reference, § 9 gate 2): a sum accumulates sequentially in row-major index order in the element type, starting from its first term, with every difference and partial sum rounded to the element type; the first product of a `matmul` or `mse` sum is rounded and starts the sum, and each later product is fused into the sum with one IEEE 754 fused multiply-add, rounded once (`mul_add`, ADR-009); `matmul` accumulates each output element over the contracting index in ascending order the same way; `mean` is that sum divided by the element count converted to the element type; `mse` is that sum of `(a-b)^2` divided by the element count converted to the element type. A sum of a whole tensor into one scalar, `reduce_sum`, `mean`, `mse` and the numerator and denominator of `cross_entropy` (and the weight sum its gradient divides by), accumulates in `f64` instead, in the same order: each term widened to `f64` exactly, an `mse` difference taken in `f64`, every partial sum and fused product rounded in `f64`, `mean` and `mse` divided by the element count in `f64`, and the result rounded to the element type once at the end (coordinator decision D84; a single `f32` running sum over the 2,097,152 squared differences of the transformer-block loss at batch 128 is 1.56e-3 off its `f64` value, outside the run tolerance of § 9 gate 5). Every reduction over a row or a column and every `matmul` element keeps the element type. A device loss sum accumulated in the element type in this order (§ 5.2) is compared with the written-out `f32` sum bit for bit (§ 5.4) and with this oracle within the tolerance of § 9 gate 5.
- Empty shapes, negative dimension sizes, integer overflows in element/byte counts, and allocations over backend limits are hard errors.

All built-in operators define forward values, gradient rules, shape constraints, precision behavior, and side effects in one operator registry (see §4). No implicit CPU fallback from a GPU-compiled plan without an explicit error or permitted fallback policy.

### 2.3 Parameters, sharing, and randomness

- Each parameter has a **stable canonical path**, e.g. `TinyMLP.fc1.weight`, independent of optimization order.
- Two `Linear` instances own distinct weights. Explicit `share(a.weight)` (post-M1) is required for tied weights; accidental aliasing is disallowed.
- Parameters have explicit initialization semantics; initial values are generated reproducibly from `global_seed + canonical_parameter_id` via the counter-based PRNG Philox4x32-10 (Salmon et al., SC 2011), **not** via compiler iteration order. `canonical_parameter_id` is the first 8 bytes of the `blake3` hash of the canonical path, read as a little-endian `u64`.
- Derivation. A draw is addressed by key and counter alone. The key is `[seed as u32, (seed >> 32) as u32]` from the `train` block's `seed`. The counter is `[index, stream, id as u32, (id >> 32) as u32]`: the element index in row-major order, a stream tag, and the 64-bit id of what is drawn. The id is `canonical_parameter_id` for a parameter and the same `blake3` id of its name for a data input. The stream tags are `0` for initial parameters, `1` for the teacher parameters of M0 synthetic data (§ 9 gate 4) and `2` for M0 synthetic inputs. Element `i` takes the block `philox4x32_10(counter(i), key)`. A uniform draw maps word 0 to `u = (w + 0.5) / 2^32` in `(0, 1)`, and `xavier_uniform` of a `[In, Out]` parameter is `a * (2u - 1)` with `a = sqrt(6 / (In + Out))`. A standard normal draw is Box-Muller over words 0 and 1, `sqrt(-2 ln u0) * cos(2π u1)`. Each value is computed in `f64` and rounded to `f32`. A tensor with more than `2^32` elements, or `xavier_uniform` on a tensor that is not rank 2, is refused.
- Initializers. A parameter's initializer is `xavier_uniform()`, which needs rank 2, or `zeros()` or `ones()`, which take any rank from 1 and set every element to `+0.0` or `1.0`. Any other initializer, or arguments to one of these, is E-TYPE-013, and an initializer on a parameter of a rank it does not take is E-TYPE-014, both at the initializer. A parameter initialized by `zeros()` or `ones()` consumes no draw and does not shift the draws of the parameters after it: it addresses no counter, it has the same value on the parameter and the teacher stream, and every other parameter keeps the bits it has without it. A checkpoint records it like any parameter.
- Stream tag `3` is masked-language-model masking, drawn anew at every step from the run seed: row `n` of the flattened batch of step `k` takes the block of counter `[n, 3, id as u32, (id >> 32) as u32]`, `id = k` on the `Train` split and `k + 2^63` on `HeldOut`; word 0 selects a row that is not a special token below `selection_rate`, word 1 picks `[MASK]`, a random token or the original token by `mask_fraction` and `random_fraction`, and word 2 picks the random token `5 + floor(w2 * (V - 5) / 2^32)` (`spec/domains/data.yaml`, `MaskingPolicy`).
- Stream tag `4` is dropout (coordinator decisions D30 and D47). Each `dropout` call with `p > 0` is a site named `<Model>.<fn>.dropout#<k>`: `<fn>` is the model function that holds the call, or `train` for a call in the `train` block's loss, and `k` is the call's index among the `dropout` calls of that function or loss in source order, calls with `p = 0.0` counted. `ir --stage tensor` prints the site on the `Dropout` node. Every inlining of a function is a site of its own, so two calls of one function draw two masks: the first inlining of `<fn>` in a program keeps the name `<Model>.<fn>.dropout#<k>`, and the second and later ones are `<Model>.<fn>@<c>.dropout#<k>`, `c` counting from 1 in the order the lowerer inlines the calls (coordinator decision D54). The draw id of a site at step `s` is the first 8 bytes of `blake3` over the site name's bytes followed by `s` as 8 little-endian bytes, read as a little-endian `u64`. Element `i` of the site's operand, in row-major order, takes the block `philox4x32_10([i, 4, id as u32, (id >> 32) as u32], key)` and is kept when `(w0 + 0.5) / 2^32 >= p`, compared in `f64`. A kept element is `x * scale` with `scale = 1.0f32 / (1.0f32 - p)`, rounded in `f32` (the `f64` reference evaluation multiplies by that `f32` scale), and a dropped one is `+0.0`. The site's RNG token is an internal input of type `i32[2]`, `[id as u32, (id >> 32) as u32]` bit for bit, that the training host computes for every site at every step; `Dropout` and its gradient `DropoutGrad` read it and recompute the mask, so no mask is stored. `p = 0.0` lowers to the identity, with no site and no token. A site of more than `2^32` elements is refused when the step runs.
- Stream tag `5` is the data order: epoch `e` visits the `n` packed `Train` sequences ascending by the 64-bit key `w1 * 2^32 + w0` of the block of counter `[i, 5, e as u32, (e >> 32) as u32]` for sequence `i`, ties by `i`, in batches of `B` consecutive positions, the incomplete last batch unused; the `HeldOut` split is read in stored order (`spec/domains/data.yaml`, `PackedDataset`). The record's `packed_id` is the version-8 UUID of `blake3` over the `Train` and `HeldOut` content hashes and `seq_len` as 8 little-endian bytes, in that order.
- Stream tag `6` is the `sigreg` projection (story:jepa-sigreg-cpu). Each `sigreg` call is a site named `<Model>.<fn>.sigreg#<k>` by the rule of dropout sites: `<fn>` the model function that holds the call or `train` for the loss, `k` its index among that function's `sigreg` calls in source order, and `<fn>@<c>` for the second and later inlinings. The site's projection is an internal `f32[K,M]` input of that name, drawn anew at every step: its draw id at step `s` is the dropout draw id of the site name and `s`, element `i = k M + m` is the Box-Muller normal of the block `philox4x32_10([i, 6, id as u32, (id >> 32) as u32], key)` in `f64`, and each column is divided by its `f64` L2 norm, the squares summed in ascending row order from row 0, each quotient rounded to `f32` once, so every column is a unit direction. The training host computes the projection of every site at every step, the last loss and a held-out or `--eval` evaluation read the step whose parameters they measure, and `infer` reads the checkpoint's step.
- Randomness used in a forward pass (e.g. dropout, post-M2) is an explicit RNG state/token. This prevents common-subexpression elimination from incorrectly merging independent random draws.
- A model specification does not do I/O. Dataset and checkpoint I/O belongs to the runtime or training host.

### 2.4 Control flow and dynamism

M0/M1 compile-time constructs (`repeat`, module instantiation, dimension generics) **elaborate statically**. Runtime data-dependent `if`/`while` and dynamically ragged tensors are out of scope. Bounded dynamic shapes may be added through specialization and recompilation. The compiler will cap specialization count to avoid unbounded code growth.

## 3. Compilation pipeline

```text
modelspec source (.mspec)
  -> lexer / parser                   [Source AST]
  -> name resolution + module expand  [Elaborated AST]
  -> tensor type/shape/effect checks  [Typed HIR]
  -> tensor SSA graph                 [Tensor IR]
  -> canonicalize, fold, DCE
  -> differentiate + optimizer step   [Training IR]
  -> whole-step optimize + liveness   [Optimized Training IR]
  -> partition/fuse + schedule/tiles  [Kernel IR + Execution DAG]
  -> target lowering                 [SPIR-V modules + manifest]
  -> Vulkan pipeline creation        [driver produces native GPU code]
  -> Rust-owned execution/runtime    [train, checkpoint, infer]
```

Passes operate on explicit immutable IR values; state transitions and synchronization are represented explicitly. Every pass has preconditions and postconditions, and the verifier runs after major transformations in debug/test builds.

### 3.1 IR levels

**Typed HIR:** source-level functions/modules with resolved types, dimension bindings, spans, and stable parameter paths. No execution layouts.

**Tensor IR:** typed SSA values with semantic ops such as `MatMul`, `Relu`, `ReduceMean`, `Transpose`, `ParameterRead`. Graph is referentially transparent except for explicit effects. Records layout constraints, not a particular layout choice. Every tensor value has a shape, dtype, and defining operation.

**Training IR:** explicit `Forward`, `Loss`, `Gradient`, `Optimizer` subgraphs for analysis, but **not** mandatory execution boundaries. Reads and writes to persistent parameter/optimizer state carry ordered effect tokens. A parameter update produces a new version of a state handle; no optimizer pass is allowed to overwrite data still required by backward computation.

**Kernel IR:** low-level loops, index expressions, dispatch dimensions, workgroup/subgroup mappings, buffer spaces, layouts, barriers, and lifetimes. A single kernel may implement multiple tensor ops, and one tensor op may require multiple kernels.

**Execution DAG:** dispatch and copy commands, resource dependencies/barriers, scratch allocations, and CPU-visible completion points. The runtime executes the DAG, not the original model AST.

M1 schedules the Kernel IR and the Execution DAG together (`schedule::schedule`, printed by `modelspec ir --stage kernel`): one buffer and one view per value and per parameter, except that the SGD update writes its parameter's buffer and view in place rather than a buffer of its own and that the fusions below store no `lr * g` product, no folded scalar, no pre-activation that only its epilogue reads, no matmul output that only its `relu_grad` epilogue reads, no transpose that only matmuls read and no value inside an elementwise chain, scalars compiled into kernels as immediates, one dispatch per computing op except for five fusions and the transpose fold, and a full barrier on every read-after-write, write-after-read or write-after-write hazard. The fusions keep every rounded value the unfused plan computes. A `relu` whose operand is a `matmul` output is an epilogue of that matmul's kernel (`epilogue Relu`): each invocation applies the same compare and select to the rounded output element before it stores it; when another op reads the pre-activation (the `relu` gradient does), the kernel writes both views (`writes pre-activation`), and otherwise only the activation, with no buffer for the pre-activation. A `relu_grad(x, g)` whose `g` is a `matmul` output that no other op reads, and that is neither the loss, the prediction nor an update, is an epilogue of that matmul's kernel (`epilogue ReluGrad`) when `x` is stored before the matmul and is no parameter updated in place before it: the kernel reads `x` as a third buffer operand, of the output's type, and each invocation applies the compare and select of the `relu_grad` kernel to `x` and the rounded output element and stores `x > 0 ? sum : 0.0`, with no buffer for `g`; the operand follows the other two on the kernel line and in the bindings, so the module id is that of a new kernel. In the MLPs this is the hidden gradient `[B, 10] x [10, H]ᵀ` and the `relu_grad` of the first layer. An SGD update `p - lr * g` with a compile-time `lr` is one `sgd_update` kernel that reads `p`, `lr` as an immediate and the gradient view `g`, and computes the product and then the difference, each rounded. An `add`, `sub` or `mul` of two compile-time scalars is folded at compile time into the immediate of its reader, when both operands and the result are finite and not subnormal and every reader takes an immediate; otherwise it stays a kernel, as a `relu` or `relu_grad` of compile-time scalars always does; the folded value is the round-to-nearest-even `f32` result, and a device test checks it against the product the unfused kernel computes on the device. A `transpose` whose every reader is a `matmul` is folded into its readers: it dispatches nothing and has no buffer, and each reader binds the transpose's operand view where the transpose's output was and reads it in place, the operand flagged `transposed` (`Kernel::transposed`). The flagged operand keeps its logical type, `[m, k]` or `[k, n]`, and its binding holds the row-major transpose of that type, so the tile, the workgroups and the counting rule do not change; the flag follows the operand type on the kernel line (`Tensor<f32, [784, 100]> transposed`) and is part of the signature, so the module id of a flagged kernel differs from that of the same matmul reading a stored transpose, and a kernel with no flag keeps its id. A transpose stays a dispatch when another kind of op reads it, when it is the loss or the prediction, or when its operand is a parameter whose in-place update comes before one of its matmul readers. The output order is unchanged: each output element of a reader is still accumulated by one invocation from the `k = 0` product in ascending `k` (§ 5.2), from the same values. A chain of elementwise ops (`add`, `sub`, `mul`, `relu` and `relu_grad`), each op but the last read once and by the next op alone, at that op's type, and neither the loss nor the prediction, is one `elementwise` dispatch at the place of its last op. An op extends the chain of its first operand, by position, that qualifies, as long as the chain reads at most 3 buffers, so that with its result it binds at most 4 storage buffers, the Vulkan minimum of `maxPerStageDescriptorStorageBuffers`, and no parameter it reads is updated in place before the op; otherwise the op starts a chain. The kernel op names the chain, its first op and then each later op with the position of the result before it among that op's operands (`Sub>Mul@0`, `Add>ReluGrad@1`), and its operands are the chain's leaves: the first op's operands in order, then each later op's operands in order without that result. Each invocation computes the ops on its element in order, each rounded once to `f32`, and keeps the values inside the chain in registers: they have no buffer and no dispatch. In an artifact compiled without `fast_math`, every `OpFAdd`, `OpFSub` and `OpFMul` of a chain is decorated `NoContraction`, so no driver contracts a product and a sum into a fused multiply-add the unfused kernels never computed; a `fast_math` artifact drops the decorations. An adjoint that sums several contributions (§ 4) is a chain of `Add`s, `((c0 + c1) + c2) + …`, added left to right, as the IR adds them, never reassociated; a sum of more than 3 buffered contributions is several chains in that order, each after the first reading the sum of the one before, and a sum that only the `ReluGrad` of its `relu` reads ends in that `ReluGrad` when the buffers fit. Nothing is fused into a matmul but the `relu` and `relu_grad` epilogues. On the MNIST example the loss gradient `(y - t) * c` is one `Sub>Mul@0` dispatch, and the step plan had 10 dispatches, 7 barriers and 13 buffers, against 11, 8 and 14 before the chain; with the `relu_grad` epilogue it has 9, 6 and 12. Why the `relu_grad` epilogue: as a kernel of its own the `relu_grad` read the matmul output and the pre-activation and wrote the gradient, three `[B, H]` views, in a barrier interval of its own after the matmul had written its output; the fused matmul reads the pre-activation once and writes the gradient alone. At `mlp_sweep` b8192 h4096 on the RTX 3090 the fused matmul took 433.9 µs against 194.8 µs for the matmul and 610.2 µs for the `relu_grad` kernel before (medians of 3 interleaved profiled runs of 1,000 steps, `benchmarks/raw/2026-10-25-step-sites/sites/`), and the step with this and the `mse` loss-sum order below took 6,858.9 µs against 6,568.5 µs for PyTorch eager (medians of 3 back-to-back runs, `benchmarks/raw/2026-10-25-step-sites/judgement/`), against 7,293.8 and 6,565.0 µs before both (`benchmarks/raw/2026-10-25-step-sites/reference/`). No product, sum or order of a sum changes, and the compare and select are those of the `relu_grad` kernel on the same rounded values, so neither does a bit: the losses, parameters and checkpoint of the MNIST example and of the sweep at 220 steps, and their `infer` output, are those before the change (`benchmarks/raw/2026-10-25-step-sites/samebits/change-2.txt`). The step plan records its ops in Training IR order but one: the `mse` loss sum, which no op of the step reads, is recorded right after the matmul with the most FLOP, the first of equals, among the ops after it up to the first that writes a buffer the sum reads or writes, reads the buffer it writes, or shares a partials buffer with it (`step_order`); without such a matmul it keeps its place. The barriers follow from the hazards as before, so the sum shares that matmul's interval, in the MLPs the weight gradient of the first layer, `[784, B]ᵀ x [B, H]`, instead of holding one of its own; the forward plan keeps Training IR order. A loss evaluation, the final loss of a Vulkan run and `infer` (§ 6), records only the steps the loss is computed from (`ExecutionPlan::loss_steps`): the step that writes the loss view, each earlier dispatch or copy that writes the prediction's buffer or a buffer a chosen step reads, and the first barrier after each chosen step that the plan orders before a later chosen step, so the gradients now recorded before the sum are not recorded there. A training step of a stepwise Vulkan run records only the steps it keeps (`ExecutionPlan::training_steps`): each dispatch or copy that writes the loss's buffer, a parameter's buffer, a buffer that a step at or before it reads (state carried to the next step), or a buffer that a later kept step reads, plus the barriers between them, chosen as for the loss steps. The full head beside a masked-row gather (§ 3.3), which only the prediction reads, therefore runs in a loss evaluation and not in a training step. A plan whose loss reads the prediction keeps every step. Why: the sum is one workgroup in which invocation 0 adds every term (§ 5.2), and in an interval of its own the device runs nothing else; at `mlp_sweep` b8192 h4096 on the RTX 3090, recorded beside the weight gradient it took the step from 7,293.8 to 7,050.5 µs (medians of 3 back-to-back runs) and 107.8 to 291.0 µs off in 4 interleaved pairs, and recorded first in that interval it took +7.0 and −149.0 µs (`benchmarks/raw/2026-10-25-step-sites/`). No kernel, operand or order of a sum changes, so neither does a bit: the losses, parameters and checkpoint of the MNIST example and of the sweep at 220 steps, and their `infer` output, are those before the change (`benchmarks/raw/2026-10-25-step-sites/samebits/`). A full reduction is four steps: an `Allocate` of its partials buffer, a stage-1 dispatch, a barrier and a stage-2 dispatch. An attention call whose kernels share softmax statistics has an `Allocate` of its `[rows · heads, 3]` statistics buffer, numbered after every other buffer, right before its `Attention` dispatch, in both plans (§ 5.2). The artifact carries two plans: the step plan, and a forward plan that computes the prediction into its own view and writes no parameter view; a forward that returns an input or a parameter copies it there (a `Copy` step), and one that returns a literal fills it. Neither plan has a completion point: each has exactly one fence, a `Barrier` with no dependencies that is ordered after every earlier step, and it is the plan's last step; `verify_plan` refuses a fence anywhere else. A runner may record a plan back to back as many times as it chooses, the recordings concatenated, each after the fence of the one before, and places completion points itself; `verify_recorded_back_to_back` checks that concatenation as one plan in which each fence closes a recording and a step with no dependencies after a fence is ordered after it. The runner uploads each batch between recordings, outside the recorded plan. Within one recording, `verify_plan` refuses a read of any parameter after its in-place update, and a dispatch whose workgroups differ from its kernel's; an `Allocate` is run setup, so it refuses one whose buffer an earlier step of the same recording used. No data, loss or prediction view lies in a parameter buffer, and each parameter and data view holds its declared type's element count; the loss view holds one element and the step plan writes it, and both plans write the prediction view. Workgroup sizes are 64 for every kernel kind but matmul, and a matmul's is that of its tile (§ 5.2), a function of its shape and of the invocation limit of the device profile the plan is scheduled for (`schedule::schedule_for`, the smaller of `maxComputeWorkGroupInvocations` and `maxComputeWorkGroupSize[0]`): 128 for every shape without a profile or under a profile at the Vulkan minimum of 128, so that plan is the plan of every device, and 256 for the block tile under a profile that allows it; the block a workgroup covers and the number of output elements each invocation computes vary with the shape; its workgroup count covers its output in blocks of the tile. The plan verifier bounds the invocations of a workgroup by the same limit (`verify_plan_for`), and by 128 without a profile.

**Tiles under the RTX 3090 profile.** `compile --device-profile <json>` and `train --backend vulkan` schedule the plan for a profile, `train` for the device it selects, and record its limits in the manifest (§ 5.2, § 7.1). Under the RTX 3090's, 1,024 invocations and 49,152 bytes of workgroup memory, a matmul takes the first tile its shape takes (§ 5.2): the block of 256 invocations, 128 rows by 128 columns, for an output of at least 128 columns with `k` of at least 64 that covers at least 128 such blocks, the bounds of the wide tile; else the wide tile, 64 by 128, on the same bounds with blocks of 64 rows; else the square tile, 64 by 64; else the one- and two-row tiles. In the `mlp_sweep` plans at b8192 h4096, b8192 h1024 and b1000 h1024 the block takes the forward matmul `[8192, 784] x [784, H]` at batch 8192 and the weight gradient `[784, 8192]ᵀ x [8192, 4096]`; the narrow matmuls `[B, H] x [H, 10]`, `[B, 10] x [10, H]ᵀ` and `[H, B]ᵀ x [B, 10]`, the other matmuls of those plans and every matmul of the MNIST example keep their tiles of 128 invocations, the shapes being too narrow or covering too few blocks. Why: the block reads half the operand values per product the wide tile reads, and with its workgroup-memory reads in vectors (§ 5.2) it is the faster tile where it applies. At b8192 h4096 it takes the forward matmul to 2,600.0 µs against 2,853.5 µs for the wide tile (20.2 against 18.4 TFLOP/s), 2,606.1 against 2,919.8 µs with `fast_math`, and the weight gradient to 2,766.6 against 3,573.6 µs (19.0 against 14.7 TFLOP/s), 2,767.5 against 3,588.2 µs with `fast_math`; the profiled steady step goes from 8,019.3 to 6,968.7 µs, while the three narrow matmuls stay at 267.5, 160.1 and 316.3 µs against 266.6, 161.6 and 317.7 µs (medians of 3 interleaved profiled runs of 220 steps against the plan without a profile, `benchmarks/raw/2026-10-25-blockperf/final/`). The bound on blocks is the wide tile's and was not measured for the block. Each element keeps one accumulator in one invocation and the order of § 5.2, so the bits of every output are those of the plan without a profile.

**Counting rule.** Every `Dispatch` step of a plan has a FLOP count and a byte count, computed from the plan when it is read (`ExecutionPlan::dispatch_count`); no field of the artifact, no artifact hash and no module id holds or depends on them. FLOP: a matmul `[m, k] x [k, n]` counts `2·m·k·n`, its epilogue adding none; an elementwise kernel and an SGD update count per output element the arithmetic they compute, one for `add`, `sub`, `mul`, `relu` and `relu_grad` (a compare and a select) and for the update `p - d`, one per op for an elementwise chain, two for the update `p - (lr * g)`; a reduction stage and the `mse` loss sum count one per element of their buffer operands; a transpose and a broadcast count none. The row-wise kernels count, over an `[n, h]` operand: `per_element` `Embedding` none, `AddRows`, `Dropout` and `DropoutGrad` one per output element, `Gelu` 10 and `GeluGrad` 24, `EmbeddingGrad` one per element of its gradient operand; `per_row` `LayerNorm` `n·(8h + 3)`, `LayerNormGradX` `n·(14h + 3)`, `Softmax` five per element and `SoftmaxGrad` four; `per_column` `SumRows` one per element of its operand and `LayerNormGradGamma` `n·(8h + 3)`, its moments counted once per row, and, over `P: [n, m]`, `SigregColumns` `m·(216n + 128)` and `SigregColumnsGrad` `m·(456n + 97)`, the instructions they emit (§ 5.2). The attention, loss and optimizer kernels (§ 5.2, coordinator decision D73) count each add, subtract, multiply, compare, division, square root, `exp` and logarithm one and each fused multiply-add two: `elementwise` `Sqrt` and `Div` one per output element; `CrossEntropy` over `[n, v]` logits `n·(4v + 3)` for its `per_row` row losses and `3n + 1` for its `loss_sum`, `n·(4v + 6) + 1` in all, and `CrossEntropyGrad` `n·(4v + 1)` for its `per_row` row statistics and `7·n·v` for its `per_element` gradient, `n·(11v + 1)` in all; with `A` heads of width `d` over `q` of `[n, h]` and `S` keys per sequence, each key counted as unmasked, `per_row` `Attention` and `AttentionGradV` `n·A·S·(4d + 5)`, `AttentionGradQ` `n·A·(S·(6d + 9) + d)` and `AttentionGradK` `n·A·S·(6d + 9) + n·h`. Bytes: the `size_bytes` of the step's read views plus those of its write views, the traffic the plan names, not DRAM traffic measured on a device. A dispatch the rule has no count for, because its kernel's op has no rule, a dimension it needs is not static, a count passes `u64`, or the plan has no kernel of its module id, is `uncounted`, never 0. `ir --stage kernel` prints `flop <n> bytes <n>` or `uncounted` on each dispatch line after its workgroups; the five matmuls of the MNIST step count 20,454,400 FLOP.

### 3.3 Compiler passes and ordering

1. Parse, resolve names, specialize compile-time dimension parameters.
2. Verify tensor shapes/dtypes/effects; lower functions/layers to tensor graph.
3. Canonicalization, constant propagation, algebraic simplification where IEEE floating-point rules allow, dead-code elimination.
4. Expand the selected loss to a differentiable graph; reverse-mode autodiff over only loss-reachable trainable values. The input adjoint, the gradient of any rank-0 target with respect to named inputs, is the same walk in a separate program (§ 4); the training program does not change. After autodiff, the `stop_gradient` removal pass (`passes::stop_gradient`) replaces each use of a `StopGradient` by its operand, in the training program and in the forward program alike, so no later pass, interpreter or schedule sees one (§ 2.2, § 4). Before autodiff, `train --masked-rows <C>` runs the masked-row gather (`passes::masked_rows::gather` through `compile::compile_training_with`; story:vulkan-mlm-masked-row-gather). When the one output is `cross_entropy(L, labels, weights)` of declared labels and weights over static logits `L: f32[N, K]` with `0 < C < N`, the pass walks back from `L` through the row-local head to its first operand, the frontier `F: f32[N, H]`. Each head node is an `add_rows`, a `matmul`, a `gelu` or a `layer_norm`, is read only by the next one, and has operands after the first that depend on no input. The pass adds the inputs `masked.rows: i32[C]`, `masked.labels.<labels>: i32[C]` and `masked.weights.<weights>: f32[C]`; their names are dotted, so no declaration can take them. It also adds `embedding(F, masked.rows)` and a copy of the head on those `C` rows that shares every row-free operand, among them the transposed tied token table. The loss node keeps its id and reads the gathered logits, labels and weights. The full head stays for the prediction that the forward program, evaluation and `infer` read. Nothing the loss depends on reads the full head, so autodiff gives it no adjoint, and the step plan records it only for a loss evaluation (§ 3.1, `ExecutionPlan::training_steps`). The frontier's gradient is the `EmbeddingGrad` of the gathered rows' gradients: a scatter into a zero `[N, H]` in ascending gathered order. The head's parameters, the tied token table included, sum their gradients over the gathered rows in ascending row order. Every step, the host fills the three inputs (`train::masked::gather`): first the rows of non-zero weight in ascending order, each with its label and weight, then padding of row 0, label 0 and weight `+0.0` up to `C`. The capacity is fixed for the run, so a batch with any count of selected rows, including none, runs the one compiled step. A batch with more than `C` selected rows is E-DATA-012 before the step; it is never truncated. An empty selection has weight sum 0, so the loss and every gradient are 0, as in the full step. Bit identity: in every sum that the full step makes over rows, a row of weight zero adds a product with a zero factor, `+0.0` or `-0.0`, which leaves a non-zero partial sum unchanged. These sums are the loss's weighted sum and weight sum in ascending row order, the weight gradients' `matmul` reductions over rows in ascending `k` with no split, and the `sum_rows` and `layer_norm_grad_gamma` row sums. The gathered step drops those terms and adds the padding rows' zeros. The loss, every gradient and every parameter after the update therefore have the bits of the full step wherever a sum is not exactly zero; where a sum is exactly zero, only its sign may differ, as in a dense gradient row the gather does not select, which is `+0.0`. Two refusal semantics change by design. First, an unselected row whose logits or head activations are not finite no longer turns the loss or a gradient into NaN through `0 × NaN` or `0 × ∞`, so E-TRAIN-001 sees only the selected rows. Second, a weight of NaN or `±∞` counts as non-zero: it is gathered and reaches the loss as before, while `-0.0` is a zero weight. Labels are still checked against the classes on every row (E-DATA-011). The final loss of a CPU run, computed with the forward program, still reads every row.
5. Attach explicit optimizer-state computations and ordered parameter updates.
6. Graph-wide dead-code elimination; forward/backward fusion candidates; liveness and recomputation analysis.
7. Choose layout, partition into kernels, tile work, plan buffer lifetimes; **repeat** some optimization after layout/scheduling.
8. Generate and validate SPIR-V, serialize execution manifest, instantiate Vulkan pipelines.

Do not silently assume `a+b == b+a` at bit level. In `deterministic` mode every floating-point reduction runs in an order fixed by the shape alone: the workgroup size of a reduction is a compile-time constant of its kernel, never read from a DeviceProfile, so one artifact gives the same bits on every run on one device and driver. The CPU order of § 2.2 is one admissible order; the two-stage GPU reduction of § 5.2 is another, and § 5.4 says which results are compared bit for bit and which within tolerance. In `deterministic` mode each product of a matmul, reduction or loss sum after the first is fused into the sum with one explicit IEEE 754 fused multiply-add, rounded once (`GLSL.std.450 Fma` on the GPU, `mul_add` in the CPU oracle, ADR-009); the first product starts the sum as a plain rounded product, not as a fused multiply-add onto `+0`, so a sum of negative zeros stays `-0`, and every operation that remains is decorated so the driver neither contracts nor splits it. `fast_math = true` is a distinct opt-in compilation setting that is recorded in the artifact hash; ADR-008 (accepted) defines what it permits, and it changes which bits an artifact gives, never whether two runs of it agree. `deterministic` is a compilation setting too: it fixes reduction order, so it is recorded in the artifact hash, and a run reads it from its artifact.

## 4. Automatic differentiation

Use **reverse-mode AD on tensor SSA**, not tape-based Python autograd. One backward graph is generated when the `train` specification is compiled. A small, explicit gradient-rule registry is a first-class compiler component.

For output adjoint `G = dL/dY`:

| Forward op | Reverse-mode contribution |
| --- | --- |
| `Y = A + B` | `dA += G`; `dB += G` |
| `Y = A - B` | `dA += G`; `dB -= G` |
| `Y = A * B` | `dA += G * B`; `dB += G * A` |
| `Y = A @ B` | `dA += G @ transpose(B)`; `dB += transpose(A) @ G` |
| `Y = relu(A)` | `dA += where(A > 0, G, 0)`; derivative at 0 **defined as 0** |
| `Y = mean(A)` | `dA += broadcast_scalar(G / numel(A), shape(A))` |
| `L = mse(Y,T)` | `dY = 2 * (Y-T) / numel(Y)`; targets receive no gradient |
| `Y = embedding(E, ids)` | `dE += embedding_grad(ids, G, V)`; `ids` receive no gradient |
| `Y = add_rows(X, b)` | `dX += G`; `db += sum_rows(G)` |
| `Y = gelu(A)` | `dA += gelu_grad(A, G)`, the derivative of the tanh form at `A` times `G` |
| `Y = layer_norm(X, gamma, beta)` | `dX += layer_norm_grad_x(X, gamma, G)`; `dgamma += layer_norm_grad_gamma(X, G)`; `dbeta += sum_rows(G)` |
| `Y = softmax(X)` | `dX += softmax_grad(Y, G) = Y * (G - rowsum(G * Y))`, reading the forward result `Y` |
| `Y = attention(Q, K, V, M, heads = A)` | `dQ += attention_grad_q(Q, K, V, M, G) = scale * dS K`, per sequence and head, with `P` the probabilities, `dP = G V^T` and `dS = P * (dP - rowsum(P * dP))` |
| | `dK += attention_grad_k(Q, K, V, M, G) = scale * dS^T Q`, exactly 0 in the row of a masked key |
| | `dV += attention_grad_v(Q, K, V, M, G) = P^T G`, exactly 0 in the row of a masked key; the key mask `M` receives no gradient |
| `L = cross_entropy(Z, labels, W)` | `dZ += cross_entropy_grad(Z, labels, W, G) = G * W[n] / sum(W) * (P[n,v] - [v = labels[n]])`, `P` the row softmax of `Z`; all 0 when `sum(W) = 0`; `labels` and `W` receive no gradient |
| `Y = dropout(X, p = P)` | `dX += dropout_grad(token, G) = G * scale` where the site's mask keeps the element, `+0.0` elsewhere, `scale = 1 / (1 - P)` as in § 2.3; the RNG token receives no gradient |
| `Y = stop_gradient(A)` | none: `A` receives no gradient through it, and the forward value is `A` unchanged; a pass after autodiff replaces each use of `Y` by `A` (`passes::stop_gradient`), so no training step, interpreter or schedule holds a `StopGradient` |
| `L = sigreg(Z, slices = M)` | lowered before differentiation: `dP += sigreg_columns_grad(P, G')` for `P = Z @ proj` and `G'` the adjoint of `SigregColumns(P)`, `2 G'[m] sum_j c_j t_j (S_j cos(t_j P) - (C_j - phi_j) sin(t_j P))` in column `m`; then the `matmul` rule; the projection receives no gradient |

`transpose`, `where`, and scalar broadcasting are explicit internal gradient ops, even if the user-facing M0 language keeps simpler syntax. So is `EmbeddingGrad`, the scatter-add of the `embedding` rule: it starts from a zero `[V,H]` tensor and adds row `G[n]` to row `ids[n]` for `n` in ascending order. A row read more than once therefore accumulates in a fixed order, and a row never read stays exactly zero. So are `SumRows` and `GeluGrad`. `SumRows` sums the rows of `G: [N,H]` into `[H]`, each column starting from row 0 and adding rows 1 to N-1 in ascending order in `f32`, every partial sum rounded, so its bits are fixed by the shape alone (§ 3.3). So are `LayerNormGradX`, `LayerNormGradGamma` and `SoftmaxGrad`, and `AttentionGradQ`, `AttentionGradK` and `AttentionGradV`, each over `q, k, v, key_mask, G`, and `CrossEntropyGrad` over `logits, labels, weights, G` (below), and `DropoutGrad` over the site's RNG token and `G`, which recomputes the mask of § 2.3 from the token and the seed. For shared graph subexpressions, **accumulate** every incoming adjoint exactly once. Treat parameters and trainable module state separately from temporary SSA tensors.

**GELU.** `gelu` is the tanh form of Hendrycks and Gimpel (2016), the form the original BERT release uses, not the exact `erf` form: `gelu(x) = 0.5 x (1 + tanh(u))`, `u = sqrt(2/pi) (x + 0.044715 x^3)`. Every backend evaluates it as the identical `x / (1 + exp(-2u))`, because in the left tail `tanh(u)` rounds to within an `f32` ulp of -1 and `1 + tanh(u)` keeps few correct bits: at `x = -3` the CPU interpreter's `tanh` evaluation in `f32` is off by `1.1e-5` relative to the form in `f64`, the `exp` evaluation by under `1e-6`. Measured for the `exp` evaluation in `f32`: under `1e-6` relative at every multiple of `1/64` in `[-3, 3]` (largest `5.5e-7`) and at every multiple of `1/1024` (largest `9.2e-7`, at `-2.9501953`), and at most `1.07e-6` over every `f32` in `[-3, -1]`, 7 of them above `1e-6`, the largest at `-2.9703214`. `1e-6` relative therefore bounds these grids, not every element; a backend compared with it at every element needs a slightly wider bound. `GeluGrad(A, G)` is `(s + 2 A s r u'(A)) G` with `s = 1 / (1 + exp(-2u))`, `r = 1 / (1 + exp(2u))` and `u'(A) = sqrt(2/pi) (1 + 3 * 0.044715 A^2)`, which equals `0.5 (1 + t) + 0.5 A (1 - t^2) u'(A)` for `t = tanh(u)`; `r` takes its own exponential so that neither tail cancels. The constants are `f32` in an `f32` program; the CPU interpreter's `f64` reference evaluation uses them to `f64` precision.

**SIGReg.** `SigregColumns(P: [N,M]) -> [M]` is the Epps–Pulley statistic of each column against the standard normal, `T_m = N int |ecf_m(t) - phi(t)|^2 w(t) dt`, with `phi(t) = exp(-t^2/2)` both the characteristic function of `N(0,1)` and the window `w`, integrated by the trapezoid rule on the 17 knots `t = -5, -4.375, ..., 5`: the PyTorch listing of LeJEPA (arXiv 2511.08544, § 4.2.3, "SIGReg with Epps-Pulley statistic"; `t = linspace(-5, 5, 17)`, `err = |ecf - exp_f|^2 exp_f`, `T = trapz(err, t) N`) and § 6.1. The integrand is even and 0 at `t = 0`, so only the positive knots `t_j = 0.625 j`, `j = 1..8`, are evaluated, with the weights `c_j = 1.25 phi_j` for `j < 8` and `c_8 = 0.625 phi_8`, `phi_j = exp(-t_j^2/2)` (§ 5.1 of the paper uses the same symmetry). With `C_j` and `S_j` the column means of `cos(t_j P)` and `sin(t_j P)`, `T_m = N sum_j c_j ((C_j - phi_j)^2 + S_j^2)`. The prose of § 4.2.3 writes the window as `exp(-t^2/sigma^2)`; the operator follows the listing. In the element type: `t_j`, `phi_j`, `c_j` and `c_j t_j` are computed in `f64` and rounded to the element type; each argument `t_j * P[n,m]` is rounded; the column sums of `cos` and `sin` run in ascending `n` from row 0 and are divided by `N`; per column, `q_j = fma(S_j, S_j, d_j * d_j)` with `d_j = C_j - phi_j`, the sum over `j` ascending is `c_1 q_1` and then `fma(c_j, q_j, sum)`, and `T_m = N * sum`. `SigregColumnsGrad(P, G)` recomputes the means through the same code path and writes `(2 G[m]) * sum_j (c_j t_j) fma(-d_j, sin(t_j P), S_j cos(t_j P))`, the sum over `j` ascending, first product rounded and each later one fused. `sin` and `cos` in `f32` are one written-out routine, not the platform's: `q = round_ties_even(x * f32(2/pi))`; Cody–Waite reduction `r = fma(-q, P1, x)`, then `P2`, then `P3`, with `P1 = 1.5703125`, `P2 = 4.837512969970703125e-4` and `P3 = 7.549789954891882e-8` (twice Cephes' `DP1` to `DP3`); `z = r * r`; `s = fma(fma(fma(S0, z, S1), z, S2) * z, r, r)` and `c = fma(fma(fma(C0, z, C1), z, C2) * z, z, fma(-0.5, z, 1))` with Cephes' minimax coefficients `S0 = -1.9515295891e-4`, `S1 = 8.3321608736e-3`, `S2 = -1.6666654611e-1`, `C0 = 2.443315711809948e-5`, `C1 = -1.388731625493765e-3`, `C2 = 4.166664568298827e-2`; and `q mod 4` selects `(s, c)`, `(c, -s)`, `(-s, -c)` or `(-c, s)`. Measured: within 1.43 `f32` ulp of `f64` `sin` and `cos` at every multiple of `1/256` in `[-64, 64]`. The routine is specified for `|x|` below `2^24 pi/2`, where the quadrant count is exact and every `f32` argument gives `|s| <= 1` and `|c| <= 1` (all of them checked), with accuracy falling from `2^9 pi/2` on; beyond it the reduction no longer bounds `r`, so `sin`, `cos` and the statistic are unspecified: measured on a column of 8 rows, finite above its bound at magnitude `1e8` and `1e9` and infinite from `1e10`, which a training step reports as E-TRAIN-001; a Vulkan kernel is to emit the same sequence, so that the device can agree with the CPU bit for bit. The `f64` reference evaluation uses the standard library's `sin` and `cos`.

**Layer norm and softmax.** Both work on each row of a rank-2 tensor in the element type, and every reduction over a row sums in ascending column order, starting from the first column, every partial sum rounded; a sum of products rounds its first product and fuses each later one into the sum with one fused multiply-add, as the `mse` sum does (§ 2.2, ADR-009). `layer_norm` takes two passes over a row of width `H` (no single-pass formula): `mean = sum(x) / H`, then `var = sum((x - mean) * (x - mean)) / H`, then `rstd = 1 / sqrt(var + eps)` with `eps = 1e-12`, an `f32` constant, the square root correctly rounded (`f32::sqrt`) and the division rounded on its own; then `y = (x - mean) * rstd * gamma + beta`, each operation rounded in that order. The value of `eps` is the original BERT release's (Devlin et al., 2019). `LayerNormGradX(X, gamma, G)` recomputes `mean` and `rstd` per row as above, takes `xhat = (x - mean) * rstd` and `gx = G * gamma`, then `a = sum(gx) / H` and `b = sum(gx * xhat) / H`, and gives `rstd * ((gx - a) - xhat * b)`. `LayerNormGradGamma(X, G)` sums `G * xhat` over the rows, each column starting from row 0 and adding rows 1 to N-1 in ascending order as a sum of products. `beta`'s gradient is `SumRows(G)`. `softmax` takes the row maximum (the first column, replaced by each later column that is greater), `e = exp(x - max)` with the element type's `exp`, `s = sum(e)` and `y = e / s`; subtracting the maximum keeps `exp` from overflowing, so `softmax` of the row `[1000, 999, 0]` in `f32` is finite and within `1e-6` of the `f64` result. `SoftmaxGrad(Y, G)` takes `d = sum(G * Y)` per row and gives `Y * (G - d)`. In `f32` the output of `layer_norm` carries the error of the ascending `f32` mean and variance: the recursive sum of a row of width `H` is off by up to about `H u |offset|` in the worst case (typically about `sqrt(H) u |offset|`, `u = 2^-24`), and normalizing divides that by the row's standard deviation, so the output's mean error is of order `H u |offset| / scale` in the worst case, with no constant that holds for every `H`. The `1e-6` mean and `1e-5` variance bounds of the scenario (`gamma = 1`, `beta = 0`) hold for rows whose offset is at most 1.5 times their scale at the scenario's `H = 5`. Two measurements on rows `-7.5 + 0.05 v`, `v` uniform in `[-1, -0.1] ∪ [0.1, 1]`, as examples, not as a bound, each a ratio to `u max|x| / s` (`s` the row's standard deviation): at `H = 5` over 1000 rows the largest mean error is `1.35e-4`, a ratio of 2.34, and the `f64` evaluation is within `1e-13`; at `H = 768` over 200 rows the operator's worst ratio is 23.6, against 0.53 for the same computation with the mean correctly rounded to `f32`.

**Attention.** All arithmetic is in the element type (`f32` on the CPU for an `f32` program) and every reduction runs in ascending index order (coordinator decision D37). `scale = 1 / sqrt(H/A)`, computed once per call, the square root and the division each rounded. For query row `i`, key row `j` of the same sequence and head `a`, the score is the dot product of the head's columns of `q[i]` and `k[j]` in ascending column order, its first product rounded and each later one fused (ADR-009), then multiplied by `scale`. The masked softmax takes the maximum over the unmasked keys in ascending order (the first, replaced by each later one that is greater), sums `exp(score - max)` over them in ascending order and divides each by the sum. The output is the sum over unmasked keys in ascending order of `p * v[j]`, fused after its first product. A masked key is skipped: where D37 gives it the probability exactly 0.0, skipping it gives the same values for every finite `k` and `v` (`s + 0 = s` and `fma(0, v, s) = s`), and the same bits except that a `-0.0` running sum stays `-0.0` where the weighted sum would give `+0.0` (`fma(0, v, -0.0)` is `+0.0` for every finite `v` of positive sign); a later Vulkan kernel reproduces the skip. In addition, no value of a masked key's `k` or `v` row, not even an infinity or NaN, reaches a result. The gradient ops recompute the probabilities through the same code path. `AttentionGradQ` takes `dP[i,j] = sum_c G[i,c] v[j,c]` and `d_i = sum_j P[i,j] dP[i,j]` over unmasked keys, then `dS[i,j] = P[i,j] (dP[i,j] - d_i)`, sums `dS[i,j] k[j]` over unmasked keys in ascending order (fused after the first) and multiplies by `scale`. `AttentionGradK` adds `dS[i,j] q[i]` into row `j` over the queries `i` of the sequence in ascending order and multiplies by `scale`; `AttentionGradV` adds `P[i,j] G[i]` into row `j` the same way. The row of a masked key in `dK` and `dV` is never written and stays exactly `+0`. The key mask is checked before the op's arithmetic, in ascending sequence and key order: a value other than 0 or 1 is a runtime error naming the sequence and the key, and a sequence with no unmasked key one naming the sequence, so no `exp` of `-inf` and no division by zero happen. With `heads = 1` and a mask of ones, `attention` is within `1e-6` (maximum absolute difference, `f32`) of `matmul(softmax(mul(matmul(q_b, transpose(k_b)), 1/sqrt(H))), v_b)` per sequence.

**Cross-entropy.** All arithmetic is in the element type and every reduction runs in ascending index order (coordinator decision D43). For row `n`: the maximum over the `V` logits (the first, replaced by each later one that is greater), the sum of `exp(logit - max)` from the first term, its `ln`, and the row loss `max + ln(sum) - logits[n, labels[n]]`, each operation rounded in that order. The numerator `sum_n weights[n] * loss_n` rounds its first product and fuses each later one into the sum (ADR-009); the denominator is the plain sum of the weights from the first; both are whole-tensor sums, accumulated in `f64` from the row losses and weights widened exactly, and the loss is numerator / denominator in `f64`, rounded to the element type once (§ 2.2, coordinator decision D84); `CrossEntropyGrad` divides by the weight sum so rounded. Rows of weight 0 are not skipped, so a later Vulkan kernel reproduces the bits without a branch (coordinator decision D46): a row of weight 0 contributes `0 * loss_n`, so its logits leave the loss's bits unchanged when its row loss is finite, and a non-finite row loss (an overflowing `max - logit`, such as the logits `3e38` and `-3e38` in `f32`, an infinite or a NaN logit) makes the loss NaN whatever the weight. The weighted sums are not normalized: weights are expected at the scale of 0 and 1 (a masked-language-model batch weights its rows 0 or 1), and weights whose products with the row losses or whose sum overflow `f32` give an infinite or NaN loss. **A weight sum of 0 gives the loss 0.0 and an all-zero gradient, not an error** (coordinator decision D30). `CrossEntropyGrad(logits, labels, weights, G)` recomputes the maximum and the sum of each row through the loss's code path and writes `G * weights[n] / sum(weights) * (exp(logit - max) / sum - [v = labels[n]])`, evaluated left to right, every element `+0` when the weight sum is 0; a row of weight 0 is not skipped here either, so an infinite or NaN logit in it makes its softmax and its gradient row NaN. A label outside `0..V`, a negative weight or a non-finite weight is a runtime error of the CPU interpreter naming the row, raised before any arithmetic of the op, rows in ascending order and the label of a row before its weight. Logits of magnitude `1e3` give a finite loss: subtracting the maximum keeps `exp` from overflowing.

**Input adjoint.** The input adjoint is the gradient of any rank-0 target with respect to named inputs instead of parameters, by the same walk and the same rules (`differentiate_inputs`). The target is the loss, or one element of the prediction built from existing ops as `sum(prediction * target_mask)`, where `target_mask` is a new input of the prediction's type that the caller binds to the one-hot tensor at the element's row-major offset (`output_element_target`). The result is a separate verified program whose outputs are the target, then the adjoint of each named input with that input's type; the training program, its outputs and what `ir --stage training` prints do not change. An input the target does not read is not refused: its adjoint is zero, `broadcast_scalar(0, shape)`. The `mse` target receives `-dY` only when it is itself named. Refused: a name that is not an input of the program (a declared input that dead-code elimination removed has none), an `i32` input (row ids have no gradient), a target that is not rank 0, a prediction that is not a value of the program, an index of the wrong rank or out of bounds, and a program that already has an input named `target_mask`.

Initial strategy: retain forward intermediates required by AD; introduce recomputation/checkpoint planning after correctness is proven. Training state writes happen only after all old-state reads are complete. Gradients accumulate in `f32` for M0/M1.

**Gradient verification:** compare CPU reverse-mode gradients to central finite differences evaluated in `f64` reference math, away from non-differentiable points. Check selected tiny graphs under seeded inputs. GPU results are checked within documented absolute/relative tolerances; § 5.4 names the results that must in addition equal the CPU oracle bit for bit.

## 5. GPU kernel compiler

### 5.1 Initial backend: Vulkan / SPIR-V

Use Rust `ash` for Vulkan API access and `rspirv` to construct SPIR-V modules programmatically. Avoid a necessary GLSL/HLSL compiler in the production compilation path. For bring-up or diagnosing unexpected SPIR-V behavior, reference GLSL and external `spirv-val` may be used as development tools.

The generated SPIR-V is **shader IR**, not the physical Ampere instruction set. The installed NVIDIA Vulkan driver owns the final machine-code compilation, internal instruction selection, and GPU submission. The compiler controls tensor-level scheduling and shader construction, not undisclosed driver internals.

Device discovery must record: vendor/device IDs, device UUID if available, driver version, SPIR-V/Vulkan feature levels, subgroup properties, FP16/storage features, cooperative matrix extensions/properties, workgroup and storage-buffer limits, timestamp support, and memory heaps/budgets. Failure to support a specialized path triggers a **correct fallback** or explicit unsupported-feature diagnostic.

### 5.2 Kernel progression

**M1 reference GPU kernels**

- Elementwise: flat-index global dispatch, explicit bounds checks, `f32` loads/stores.
- Reductions (`sum`, `mean`): 2-stage reduction. Stage 1 reduces each block of 64 consecutive elements in a pairwise tree in workgroup memory (at stride 32, 16, … 1, invocation `i` adds value `i + stride` when it exists) and writes one partial per workgroup; stage 2 is one workgroup of 64 in which invocation `i` sums partials `i`, `i + 64`, … in ascending order, then the same tree folds the 64 sums, and `mean` divides by the element count. No padding term is added and there are no atomics, so the order is fixed by the shape alone (§ 3.3).
- `mse` loss sum: one workgroup of 64 invocations stages the differences `a - b` in workgroup memory, in chunks of at most `maxComputeSharedMemorySize / 4` terms with a barrier after each staging, and invocation 0 adds the terms `(a - b) * (a - b)` in row-major order from the first term, each later term's product fused into the sum (`GLSL.std.450 Fma`, ADR-009), then the division by the element count.
- Matmul: each output element accumulated by one invocation, bounds-checked on both output dimensions, over ascending `k`, starting from the `k = 0` product and not from zero; no split-K. The M2 tiling below, done in M1. An output that takes neither register-blocked tile of the next paragraph: a workgroup of 128 invocations computes a block of 8 rows by 16 columns (fewer columns, a power of two, when `n` is smaller), or of 16 rows, two per invocation each with its own accumulation, when the block of 8 rows needs at least 256 workgroups: on the RTX 3090 two rows take the `[784, 100] x [100, 64]` matmul of the MNIST example (392 workgroups of 8 rows) from 5.24 to 4.92 µs and are slower at its other four matmuls of at most 52 workgroups (11.4 against 8.6 µs at the forward one, means of 3 profiled runs of 144,000 steps); staging tiles of up to 64 values of `k` of both operands in workgroup memory, `b` transposed with its columns padded to a multiple of 4 plus 4 against bank conflicts (without the 4, the forward matmul of the MNIST example takes 27.0 against 11.6 µs, means of 3 alternating profiled runs of 144,000 steps); each tile is read into registers 6 tiles ahead and staged in one of two buffers, with one barrier per tile. A tile of two rows per invocation takes tiles of up to 16 values of `k` read 2 tiles ahead instead: on the RTX 3090 they take the `[784, 100] x [100, 64]` matmul from 4.91 to 4.58 µs against tiles of 32 read 6 ahead (medians of 3 profiled runs of 144,000 steps). From the second tile on, the full tiles that read a full tile that many tiles ahead run in a loop of passes of 4 tiles, the reads not yet staged carried from pass to pass in function variables, and the tiles before, after and between are emitted straight, so the size of a module is bounded whatever its `k`. Depth halves until the tile fits the 16 KiB every Vulkan device provides, and a tile larger than the device profile's `maxComputeSharedMemorySize` is refused before any pipeline is created. Register blocking: an output of at least 128 columns, with `k` of at least 64, that covers at least 128 blocks of 64 rows by 128 columns takes the wide tile, 128 invocations each accumulating 8 rows by 8 columns in registers, with tiles of 8 values of `k`; any other output of at least 64 columns that covers at least 128 blocks of 64 by 64 takes the square tile, 8 rows by 4 columns per invocation, with tiles of 16 values of `k`. Every output of at least 1024 by 1024 takes one of the two. An invocation's columns are strided by the 16 invocations of a row of the workgroup and its rows by the 8 such rows; each tile of `b` is staged `k`-major, unpadded, read 1 tile ahead, and the 8 or 4 values of `b` an invocation needs for one `k` are read once and used by its 8 rows. Each element still has one accumulator in one invocation, so the bits are those of the one-column tile; a device test compares 22 matmuls with digests recorded before the change. The reader refuses a plan with a workgroup past the recorded invocations (E-ARTIFACT-003), and a device that reports fewer invocations or less workgroup memory than recorded is refused before any module is built or dispatched (E-ARTIFACT-005, naming the recorded and the reported value of both). Values outside the matrices are staged but enter no written output, and the last tile has its own trip count, so the sum of each element is the order above. A matmul reads an operand flagged `transposed` (§ 3.1) in place, `a` bound as `[k, m]` or `b` as `[n, k]`: its staging reads the operand's contiguous index fastest, the tile's `k` of `b` and, of `a`, 8 of the block's rows (one 32-byte sector) at one `k`, then the next `k`, then the next 8 rows, so consecutive invocations read consecutive addresses as they do for an operand read as is; each value goes to the line and place in its line where the operand read as is puts it in workgroup memory, so the products read the same values, and every product and the order of each sum are those of the stored transpose. The lines of a flagged operand are padded against bank conflicts when the padded tile fits the device's workgroup memory (otherwise they keep the stride of the operand read as is): a transposed `a` stores 8 rows by 4 values of `k` per subgroup, and with a depth that is a multiple of 4 its stride is the smallest one of at least the depth that leaves 4 modulo 8 (12 for 8, 20 for 16, 68 for 64); a transposed `b` of a register-blocked tile stores `32 / depth` columns of `depth` values, `k`-major, and with a depth of 2 or more that divides 32 its stride is `cols + 32 / depth`; so the 32 stores of a subgroup fall into 32 different banks, where the unpadded strides put 2 to 16 into one bank. **M2 optimized kernels**

- Workgroup tiling and shared-memory staging for matmul (done in M1, above); choose tile size to fit shared memory and register pressure. In `deterministic` mode one invocation accumulates each output element over the contracting index in ascending order, tile after tile, and the contracting index is not split across invocations (no split-K), so the order of § 2.2 holds.
- Fuse elementwise chains and simple epilogues (e.g. `matmul + relu`) if compiler cost estimates permit. M1 already runs each chain of elementwise ops whose values inside have one reader as one dispatch, an adjoint's sum among them, and the `relu` and `relu_grad` epilogues (§ 3.1), the latter `ReluGrad` into the matmul that produces its adjoint; the other fusions into a matmul below are still M2. For a training step this includes `relu` into the loads of its consumers, the MSE gradient `(Y - T) * c` into the matmul that produces `Y`, and the SGD update `p - lr * g` into the matmul that produces `g`, so `g` is not written to device memory.
- Gather operands in the matmul load: minibatch rows are read from the resident data set through the resident permutation (§ 6.3), with no separate minibatch copy.
- Plan layouts and alignment, avoid unnecessary global writes, batch compatible kernels.
- Tune with GPU timestamp queries; measure registers/occupancy via external profiling where practical.

**M4 hardware specialization**

- Probe `VK_KHR_cooperative_matrix` or applicable vendor extension at runtime; enumerate *actual supported* matrix types and M/N/K shapes.
- Dispatch cooperative-matrix tiled matmul only in a `fast_math` artifact (ADR-008) and only on devices with a validated implementation. Do not assume a specific driver exposes this extension merely because the GPU has Tensor Cores.
- Incorporate f16 storage/compute with explicit accumulation and stability rules. Do not assume bfloat16 is available in the initial Vulkan path.

### 5.3 Fusing and partitioning

Fusion is cost-driven, not automatic: fewer launches and intermediate writes may lose to increased registers, workgroup occupancy, or duplicate computation. Kernel partitioning considers memory traffic, tiling compatibility, operation shapes, shared-memory footprints, register estimates, and dependency barriers.

M1 uses a fixed safe schedule; M2 measures alternatives; M4 supports offline/autotuned specialization. Kernel configuration cache keys include IR hash, shapes, dtype, optimization settings, GPU/vendor/driver identifiers, and extension/capability set.

### 5.4 GPU results compared bit for bit and within tolerance

The CPU oracle is the reference for every GPU result (§ 9 gate 5). Which comparison applies is fixed by the instructions that produce a result and by the device's queried features:

1. **Bit for bit.** In `deterministic` mode, on a device that reports `shaderRoundingModeRTEFloat32`, `shaderDenormPreserveFloat32` and `shaderSignedZeroInfNanPreserveFloat32`, kernels declare the execution modes `RoundingModeRTE`, `DenormPreserve` and `SignedZeroInfNanPreserve` and decorate every `OpFAdd`, `OpFSub`, `OpFMul` and `GLSL.std.450 Fma` with `NoContraction`. Vulkan specifies the first three instructions as correctly rounded and comparisons as exact (Reference 1); `NoContraction` forbids contracting them into a fused multiply-add and rearranging them. Each product after the first of a matmul, reduction or loss sum is one `Fma` (ADR-009), which the CPU oracle computes with `mul_add`, the IEEE 754 fused multiply-add rounded once; that a device computes `Fma` that way is established by the oracle comparison on that device (`vulkan_fma_oracle`, every matmul site and loss sum of the MNIST and `mlp_sweep` step plans, which the RTX 3090 passes bit for bit), not assumed for every device. A result built only from these instructions, copies and selects, in the order of § 2.2 with each later product fused, equals the CPU oracle bit for bit. For a training step these are: the gathered minibatch and its one-hot targets, every `matmul` output without split-K, `relu` and `ReluGrad` as compare and select, `sub`, `mul` by the gradient scale of `mse` (folded to a constant at compile time), the SGD update, the parameters after every step, and a loss sum accumulated by one invocation in row-major order.
2. **Within tolerance.** Every other result is compared within the tolerances of § 9 gate 5: a result that passes through `OpFDiv` (Vulkan bounds it at 2.5 ULP; in a step only the `mse` and `mean` values, which no gradient reads), a transcendental function, any parallel or split reduction, any `fast_math` artifact, and every result on a device that lacks one of the three features. The run record names the class the run used. `SigregColumns` and `SigregColumnsGrad` (§ 5.2) are in this class: their column means pass through `OpFDiv`, and the gradient reads them; their element `r` is the sum of the absolute values of its terms, each weighted by how much the element moves with it (`vulkan_sigreg`), and a training run with `sigreg` is held to the run tolerance of § 9 gate 5.
3. A bit-for-bit result also passes the tolerance check: this adds to gate 5 and replaces nothing in § 9. Cooperative-matrix kernels (§ 5.2, M4) are never in the bit-for-bit class, and the M2 schedule does not use them.

In M1 the bit-for-bit class holds the `mse` loss sum before its division and every matmul output. M1 emits `RoundingModeRTE`, `DenormPreserve` and `SignedZeroInfNanPreserve` for width 32 on those two kernels exactly when the device profile reports the three features, decorates their `OpFAdd`, `OpFSub`, `OpFMul` and `Fma` with `NoContraction` on every device in an artifact compiled without `fast_math`, and the operator run asserts their bit-equality against the CPU when `negotiate` gives the class `bit-for-bit`. The CPU interpreter accumulates the `mse` sum in `f64` (§ 2.2, coordinator decision D84), so the device loss sum is held bit for bit to the written-out `f32` sum in the order of § 2.2, and the loss after its division to the interpreter within the tolerance of § 9 gate 5. A `relu` or `relu_grad` epilogue (§ 3.1) runs inside the matmul kernel, under its execution modes; each is a compare and a select, no arithmetic. That a fused kernel leaves the bits of the unfused plan is verified only on a device where the matmul kernel declares none of `DenormPreserve` and `SignedZeroInfNanPreserve`: the RTX 3090 reports `shaderDenormPreserveFloat32` false, so M1 emits no float-control mode there, and the epilogues under those modes are untested. The fused `sgd_update` decorates its `OpFMul` and `OpFSub` with `NoContraction` on every device, so the product is rounded before the difference. A fused elementwise chain decorates each of its `OpFAdd`, `OpFSub` and `OpFMul` the same way, and writes the bits the unfused kernels write, one per op with each value inside the chain stored: `vulkan_elementwise_chain_same_bits` compares the two on the device for every chain form at six element counts, zeros of both signs, infinities, NaN and subnormals among the operands, and the RTX 3090 passes bit for bit; without the decorations its driver contracts `a * b + c` and 32,987 of 661,520 elements differ. The kernels of a `fast_math` artifact carry none of these decorations and nothing else in them changes (ADR-008): they emit the same `Fma`, so nothing of a matmul's inner loop is left for the driver to contract. Two-stage reductions, the `mse` value after its division and every other M1 kernel are checked within tolerance.

## 6. Rust runtime design

The runtime has four owned responsibilities:

**Device:** Vulkan instance/device/compute queue selection, feature negotiation, shader modules, pipeline cache, command pools, and error reporting. Prefer a compute-only headless configuration; no graphics swapchain. The runtime requires Vulkan API version 1.2.0 and refuses a device below it (E-TARGET-004). The enabled set is the required version, no optional device feature, no device extension and one queue from the first compute queue family; a later capability that needs a feature or extension adds it to the set with the story that uses it. Negotiation also fixes the numerics class of § 5.4: `bit-for-bit` when the device reports all three float-control values, `tolerance` otherwise.

**Memory:** device-local tensor arena, staging buffers for host upload/download, allocations obeying Vulkan heap/buffer-range/alignment restrictions, liveness-based scratch-buffer reuse, bounds/overflow checks, and out-of-memory diagnostics. Keep checkpoint and optimizer state in separate logical arenas even if physically suballocated.

**Execution:** execute compiled DAG nodes (uploads, dispatches, barriers, reads); construct descriptor resources, push constants, specialization constants, command buffers, and synchronization. Use appropriate transfer/compute barriers (e.g. synchronization2 when available). No hidden host synchronization between operators or between steps: from M1 a training run on a device waits on the host once (§ 6.3 items 4 and 5). The M1 runner executes the artifact's plans as they are scheduled. At setup it makes one device-local buffer per plan buffer, which runs the step plan's `Allocate` steps once, uploads the initial parameters and the synthetic batch once from one staging buffer, and binds every dispatch of the step plan once in one descriptor pool. Each step records the step plan, a plan barrier as a compute-to-compute memory barrier and a plan copy between transfer barriers, then copies the loss into slot `k` of a device-local buffer of `steps + 1` slots. After the last step it records the steps of the step plan the loss is computed from (§ 3.1), which write no parameter, for the loss of the final parameters into slot `steps`, then copies the parameters and the loss slots to one staging buffer. Up to 256 steps go into one command buffer; the command buffers are submitted to the one queue one after the other without a fence, the last behind the run's only fence, and the host waits on it once and reads everything back. The run counts its host waits, submits, dispatches and the bytes copied up and down; `train --stats` prints them (§ 8). Its results are compared with the CPU run within tolerance, so a training run is in the `tolerance` class of § 5.4 on every device: its losses are `mse` values after their division, and its SGD updates and elementwise kernels are outside the M1 bit-for-bit set of § 5.4.

**Training host:** data batching interface, seed/state initialization, step counter, loss telemetry, checkpoint save/reload, and inference entry point. Host is Rust; model does not invoke arbitrary host callbacks in M1. On the CPU the batching interface feeds a step synthetic data, dense `f32` files or a packed masked-language-model batch (§ 8): step `k` of a packed run feeds the `f32` tensors `key_mask` and `weights` and the `i32` tensors `ids`, `positions` and `labels` of the batch of step `k`, a pure function of the packed data, the masking policy, the run seed, `k` and `B` (§ 2.3), so the inputs of a step hold tensors of both element types and a resumed run draws the batches of the run that never stopped.

**Optimizer state:** SGD has none. AdamW keeps a first moment `m` and a second moment `v` for every parameter with a gradient, each of the parameter's type and `0.0` before the first step. They are state of the step like the parameter itself: the step reads each as an `Input` of the `Optimizer` subgraph (`optimizer.m@<path>`, `optimizer.v@<path>`) carrying a read effect at the parameter's version `n`, and writes its next value as an output carrying a write effect at version `n + 1`, every read token before every write token, so the moments advance with the parameter, one version per update. The host holds them beside the parameter values and hands them back each step; a run prints and checkpoints the parameters only, and a checkpoint has no optimizer slots yet, so an AdamW run takes neither `--checkpoint` nor `--resume` (§ 6.2, coordinator decision D50), except `--checkpoint` on a run of `--steps 0` without `--checkpoint-every`, whose moments are still 0: it writes the initial parameters with no optimizer slots, the parameters an opponent starts from (story:bert-tiny-vs-pytorch-cuda). The moments are not checkpointed yet, so a resumed AdamW run is refused before its first step wherever it is asked for, the runtime library too: moments restarted at 0 would take the bias corrections of the resumed step (exit 1 should it reach the CLI). A checkpoint of an AdamW file records its optimizer as AdamW with its hyperparameters and schedule, so an SGD checkpoint does not resume into it, nor an AdamW one into an SGD file (E-CKPT-003). A moment that is NaN or ±inf after an update stops the run with E-TRAIN-001 (§ 8.1). A step whose loss reads no parameter has no update, no moment and no host input under AdamW, and trains as it does under SGD (coordinator decision D64).

Muon keeps a momentum buffer `b` for every parameter that takes Muon (§ 2.1), of the parameter's type and `0.0` before the first step. The step reads it as `optimizer.b@<path>` and writes its next value under the same effect rule as the moments. A Muon parameter has no `m` and no `v`, and the parameters a `muon` file trains with AdamW keep theirs as above. In parameter order, the step's state outputs are `m` then `v` for each AdamW parameter and `b` for each Muon parameter. A checkpoint does not hold `b` either. So a Muon run takes neither `--checkpoint` nor `--resume`: the CLI refuses them as a usage error of one line, exit 2, and the runtime library refuses a resumed Muon run before its first step. A checkpoint of a Muon file records its optimizer as Muon with its hyperparameters, so no checkpoint of another optimizer resumes into it (E-CKPT-003). A momentum buffer that is NaN or ±inf after an update stops the run with E-TRAIN-001.

Proposed API boundary:

```rust
pub struct TrainConfig {
    pub steps: u64,
    pub seed: u64,
    pub checkpoint_every: Option<u64>,
}

pub trait DeviceRuntime {
    type Compiled;
    type Error;
    fn load(&mut self, artifact: &CompiledArtifact)
        -> Result<Self::Compiled, Self::Error>;
    fn execute_step(&mut self, program: &mut Self::Compiled,
                    inputs: &Batch) -> Result<StepMetrics, Self::Error>;
}
```

`steps` counts the steps of one invocation, so a run resumed at step `s` ends at `s + steps`. This interface is illustrative; use opaque handles rather than exposing raw Vulkan objects to the training host. The CPU backend implements equivalent observable training semantics for debugging.

### 6.1 Reproducibility

Record source/compiler version, tensor shapes, optimizer hyperparameters, RNG algorithm/seed/state, model/parameter identifiers, step number, backend/device/driver, and compile flags. A seeded training run should be reproducible **under a documented fixed configuration**, not promised bit-identical across CPU and GPU or different drivers, except for the results § 5.4 compares bit for bit on a device that reports the features it names. `deterministic` mode (a compile flag, § 3.3) disables nondeterministic algorithms where controllable, but driver-dependent floating-point behavior still applies.

### 6.2 Checkpoint format

Versioned binary package `.msckpt`:

- header: magic `MSCK`, format version, endian marker, manifest size, checksum/hash (`blake3` over the header and manifest bytes, the checksum field itself counted as zero bytes);
- structured manifest (JSON for M1): compiler/model schema hash, parameter names, shapes, dtypes, offsets/lengths, optimizer state descriptors, RNG and step state;
- contiguous little-endian tensor payload with explicit alignment;
- optional verification hash of payload.

Tensor offsets are absolute file offsets. Validate offset and size ranges against file size before mapping/allocating. Load into CPU backend even if checkpoint was made on GPU. Parameter-path migration between incompatible model definitions requires an explicit adapter; never silently reinterpret tensor bytes.

Format version 1 (M1). The header is 56 bytes, every integer little-endian:

| Offset | Width | Field |
|---|---|---|
| 0 | 4 | magic, the bytes `MSCK` |
| 4 | 4 | format version, `u32` `1` |
| 8 | 4 | endian marker, `u32` `0x01020304`, so the bytes `04 03 02 01`; the bytes `01 02 03 04` mark a big-endian file, which is refused |
| 12 | 4 | reserved, zero |
| 16 | 8 | manifest size `m`, `u64`, the bytes of the manifest |
| 24 | 32 | checksum, `blake3` over bytes `0 .. 56 + m` with these 32 bytes counted as zero |

The manifest is compact UTF-8 JSON at byte 56 (`spec/domains/checkpoint.yaml`, `Checkpoint`): `checkpoint_id`, `file_size`, `alignment`, `schema_hash` (the artifact's, `story:m1-kernel-plan`), `step`, `payload_hash`, `optimizer`, `optimizer_slots`, `rng` and `parameters`, each record its `path`, `dtype`, `shape`, `offset` and `length`, in path order. The alignment is 64 bytes: the payload starts at the first multiple of 64 at or after `56 + m`, every tensor offset is a multiple of 64, the gaps are zero bytes, and the file ends with the last tensor. M1 always writes `payload_hash`, `blake3` over the bytes from the payload start to the end of the file. `checkpoint_id` is a version-8 UUID derived by `blake3` from the whole manifest with the nil UUID in its place, optimizer, `rng` and payload hash included, so two runs that reach the same state write the same bytes and two checkpoints that differ anywhere carry different ids. A shape has at most 8 dimensions. M1 SGD has no optimizer slots, `optimizer.schedule` is absent, and `rng` is the seed with counter 0, because an SGD step draws no number.

A reader refuses, before it allocates a tensor and in this order: a bad magic, version, endian marker or reserved field (E-CKPT-001); a file shorter than the header or a manifest size past the end of the file (E-CKPT-002); a checksum that differs (E-CKPT-001); a manifest that is not the JSON above, has no `payload_hash`, a `checkpoint_id` that is not a UUID or a shape of more than 8 dimensions, or breaks an invariant of `Checkpoint` (E-CKPT-001), and one with more records than a file of its size can hold, which is refused before the records are kept so that no single allocation grows past the file size plus 4,096 bytes (E-CKPT-002); a `file_size` other than the file's, an alignment other than 64, or an offset or length that is misaligned, overlaps the header, the manifest or another tensor, ends past the file, or is not the shape's element count times the dtype size, a file that does not end at its last tensor, and a byte between the manifest and the first tensor or between tensors that is not zero (E-CKPT-002); and a payload hash that differs (E-CKPT-004). A checkpoint loads into a compiled file only with the same parameter paths, dtypes and shapes and the same schema hash, and a resumed run also needs the same optimizer; the first difference is refused with E-CKPT-003.

### 6.3 Whole-run execution (M2)

M2 executes a training run, or a requested number of its steps, with no host round-trip per operator or per step. M1 already records a run on synthetic data that way (§ 6, Execution): items 4 and 5 say what holds from M1 and what M2 adds. M2 changes the schedule only: every kernel computes the ops of the verified training IR (§ 0 invariants 1 and 5), and § 5.4 says which results equal the CPU oracle bit for bit.

1. **Resident state.** The data set, its labels, the permutation of every epoch the run covers, two versions of each parameter and one loss slot per reported step are uploaded once before the first step and stay in device-local memory; the allocator checks them against the heap budget (§ 6, Memory). For the MNIST benchmark example that is 188,160,000 bytes of images and 720,000 bytes of permutation. The upload is loading, outside the timed region of ADR-007.
2. **Gather on the device.** Step `s` reads its minibatch rows through `permutation[s * B + r]` in the operand load of its first matmul (§ 5.2), and builds its one-hot targets from the labels the same way. The permutation is the shuffle order of the data binding, computed on the host. The gather is a runtime data binding, not a Tensor IR op (§ 2.3: a model does no I/O).
3. **Parameter versions.** Step `s` reads version `s mod 2` of each parameter and writes version `(s + 1) mod 2` (§ 3.1). Two buffers replace an in-place update because the kernel that updates `W2` runs beside the kernel that still reads the old `W2`.
4. **Recording.** The host records the steps in chunks, one command buffer per chunk, with a compute-to-compute memory barrier between dependent dispatches. It records chunk `n + 1` while the device executes chunk `n` and submits it to the same queue. The host waits only at the end of the run, at a checkpoint (§ 6.2) and at a requested read-back; a checkpoint ends a chunk. Steps are not merged into one dispatch behind a device-wide barrier, because Vulkan does not guarantee that the workgroups of one dispatch run at the same time. From M1: chunks of 256 steps, every command buffer submitted without a fence but the last of each segment, a segment ending at each step `--checkpoint-every` requests and at the end, and one host wait per segment; an M1 run has no other requested read-back on the device. M2 adds the step index in a push constant, which the gather of item 2 reads.
5. **Read-back.** Parameters are read back at the end and at each checkpoint. On a reported step (§ 8) the loss is written to its slot and read back with the parameters; the `step <k> loss <v>` lines keep their content and order and are printed after that read-back. Per-kernel timing uses timestamp queries on sampled steps (§ 0 invariant 7). From M1: the parameters and every step's loss, `steps + 1` slots, are read back once at the end, the parameters also at each checkpoint, and `--serve` streams the `StepCompleted` events after the last read-back. M1 `train --profile` writes the timestamp queries on every step and reads them back after the last wait (§ 8). M2 writes only the reported steps' losses, and samples the timestamp queries.
6. **Schedule of the benchmark example.** Four dispatches per step, each a tiled shared-memory kernel (§ 5.2) with its elementwise ops fused. `X_b` and `T_b` are gathered as in item 2; `c` is the compile-time gradient scale of `mse`.

   | kernel | computes | writes |
   | --- | --- | --- |
   | K1 | `A = X_b @ W1` | `A` |
   | K2 | `dY = (relu(A) @ W2 - T_b) * c`; on a reported step also the loss sum | `dY`, loss slot |
   | K3 | `dA = ReluGrad(A, dY @ transpose(W2))` and, in other workgroups, `W2' = W2 - lr * (transpose(relu(A)) @ dY)` | `dA`, `W2'` |
   | K4 | `W1' = W1 - lr * (transpose(X_b) @ dA)` | `W1'` |

   If the four dispatch boundaries cost more than their budget, every K4 workgroup recomputes `Y`, `dY` and its columns of `dA` itself (at most 0.256 MFLOP per workgroup, from the shapes), one workgroup also writes `W2'`, and a step has two dispatches. The same ops in the same order keep § 5.4's class; § 5.3 decides between the two schedules by measurement.
7. **Budget.** ADR-007's gate is 51.9 µs per step. The work column is arithmetic from the shapes; every µs figure other than the gate is an estimate, not a measurement, and the first M2 benchmark replaces it.

   | part of a step | work per step | budget, µs |
   | --- | --- | --- |
   | K1 | 10.04 MFLOP; reads 313,600 B of `X_b` and 200,704 B of `W1` | 12 (estimate) |
   | K2 | 0.13 MFLOP | 3 (estimate) |
   | K3 | 0.26 MFLOP | 3 (estimate) |
   | K4 | 10.04 MFLOP; reads 313,600 B of `X_b`, writes 200,704 B of `W1'` | 12 (estimate) |
   | four dependent dispatch boundaries | barrier, drain and launch | 12, 3 each (estimate) |
   | host recording, submission and waits not hidden behind device work | | 2 (estimate) |
   | loss sum on reported steps | 1,000 terms on about 37 of 1,800 steps | 0.5 amortized (estimate) |
   | read-back at the end | 203,264 B of parameters and the loss slots | 0.5 amortized (estimate) |
   | reserve | | 6.9 |
   | total | 20.45 MFLOP | 51.9 (gate) |

   Derived from the table: the gate needs 394 GFLOP/s over a whole step, and K1 and K4 at 12 µs each run at about 0.84 TFLOP/s. Without fused multiply-add (§ 5.4) a multiply and an add are two instructions, so the usable `f32` peak is about half of the device's fused figure, about 17.8 TFLOP/s (estimate: half the vendor's 35.6 TFLOP/s, not read from a file). Without split-K each of K1's 6,400 output elements is one chain of 784 dependent additions, about 1.8 µs at 4 cycles per addition and 1.7 GHz (estimate). The dispatch boundaries are the largest unmeasured item; M2 measures a chain of empty dependent dispatches in one command buffer before it writes the kernels.

### 7.1 Key API and ownership rules

- Compiler passes take immutable or explicitly mutable owned IR, never shared global mutable graph state.
- The compiler emits a `CompiledArtifact { manifest, kernels, plan }`; the runtime never reparses source. A CPU-backend artifact has no kernels and its plan has no dispatch steps. Each parameter has one or two views (two admit ping-pong updates, § 6.3; M1 emits one), each data input and target one, and the artifact names its loss and prediction views; the schema hash covers parameter paths, dtypes and shapes only, so it is equal across backends and learning rates.
- `CompiledArtifact` is versioned. Untrusted serialized artifacts are validated before dispatch. On disk an artifact is a directory: `artifact.json` (format version 1) and, for Vulkan, `kernels/<kernel_module_id>.spv`, one per kernel, its words little-endian; `compile` removes the `artifact.json` and `kernels/` of an earlier artifact in the output directory before it writes, so the directory holds exactly the new artifact. The manifest holds the format version, `artifact_id`, `backend`, `artifact_hash`, the source, IR and schema hashes, `fast_math`, `deterministic`, `matmul_limits` (`invocations` and `shared_bytes`, the limits of the device profile the plan was scheduled for, § 5.2; absent for a plan scheduled for every device, so a compile without a profile writes the manifest it wrote before), `compiler_version`, the parameters, data, kernels (module id, entry point, cache key, byte length, blake3 and the Kernel IR, an `f32` immediate by its bits), the step and forward plans, the buffer sizes and the loss and prediction views. `artifact_hash` is blake3 over the pretty-printed JSON of the manifest with `artifact_hash` and `artifact_id` empty, followed by each module's bytes in id order; `artifact_id` is its first 16 bytes as a version-8 UUID. The hash detects an artifact changed after it was written; it does not authenticate one. `modelspec_core::artifact::read` checks, in order: the manifest a regular file and the format version (E-ARTIFACT-001); each of the step and forward plans has at most 4,096 steps, 65,536 dependencies and 65,536 views (reads and writes summed over its steps), counted as the manifest is parsed so that a plan past them is refused without being held, sealed or not (E-ARTIFACT-003); every module file present, a regular file and no longer than its entry, and no entry in `kernels/` that no kernel names, before any module is hashed, no read going past an entry's byte length (E-ARTIFACT-004); each module's blake3, then `artifact_hash` and `artifact_id` (E-ARTIFACT-002); then every byte size fits in 64 bits, the invariants of `spec/domains/artifact.yaml` (no buffer over 4294967295 bytes and no `matmul_limits` below 128 invocations or 16,384 bytes, the error naming the field and its bound, among them), every Dispatch names a module the artifact owns, every module is SPIR-V (whole words, a 5-word header, the magic number 0x07230203), and the plan verifier, which bounds workgroups by the recorded `matmul_limits` invocations, or by 128 without them (E-ARTIFACT-003). `read_for_device`, which `compile --device-profile` reads back with, then refuses a device that reports fewer invocations or less workgroup memory than recorded (E-ARTIFACT-005, naming the recorded and the reported value of both), and the same check (`check_device`) runs before a Vulkan run opens its device. Two compiles of one file on one device profile write byte-equal directories.
- The plan verifier's work is bounded by the plan, so the reader's limits bound it on an untrusted artifact. Each pass keeps what it needs of the steps before the current one (the buffers its recording used or allocated, the last stage 1 per buffer, the readers of each parameter, the first update per buffer in the recording, the Dispatch and Copy steps that touch each buffer), and the steps each step is ordered after are bit sets. Its time and memory grow with the steps times the steps, dependencies and views, over 64: at the limits the two step-by-step bit sets take 4 MiB, and the six plans of 4,096 steps in the shapes that load a pass most, an unsynced pair of Copy steps at the view limit among them, verified in 0.015 s to 0.162 s each in a debug build (three runs, 2026-10-23). In those runs the reader refused a sealed 64 MiB manifest of 33.5 million dependencies in 2.4 s to 4.5 s, at most 71 MiB resident. The other arrays of the manifest have no limit yet: a sealed 64 MiB manifest that fills a parameter or data shape or an array of a kernel's cache key took the reader longer than 10 s or more than 1 GiB, and one that fills the buffers 8.3 s and 518 MiB. The limits are 186 times the largest plan an example compiles to, the 22-step MNIST step plan. The compiler does not refuse a plan past them yet; `compile` would write it and its own read-back refuse it with E-ARTIFACT-003.
- GPU resources are RAII-owned; destruction waits for or tracks in-flight use. Hide unsafe Vulkan calls behind compact, tested abstractions.
- Every buffer view stores dtype, logical element count, allocation range, alignment, and device ownership; the public API prevents mixing incompatible buffer views.
- No raw unvalidated source-level pointer arithmetic or user-injected SPIR-V in M1.

A function that calls `sigreg` reads, at every site, the projection of the checkpoint's step (§ 2.3), on both backends. On Vulkan the function's step runs stepwise with 0 steps from the checkpoint's step (`vulkan::stepwise`): one command buffer and host wait per block, its result read back before the next, and one for that step. On Vulkan a checkpoint ends a segment of the run: the host waits once for it, reads the parameters back and writes the file, then records the next segment from the parameters still on the device, so a run with `--checkpoint-every` waits once per such checkpoint and once at the end, and a resumed device run passes against the run that never stopped within the whole-run L2 bound of § 9 gate 5 for its final parameters and the tolerance of § 9 gate 5 for each loss. `infer <file> --backend vulkan [--device <index>] --checkpoint <path>` reads the checkpoint before it opens the loader, so a checkpoint the CPU refuses is refused with the same E-CKPT code; it then runs the steps of the step plan the loss is computed from (§ 3.1) once on the device, with one host wait, and prints the same two lines, each value within the tolerance of § 9 gate 5 of `--backend cpu`'s. A build without the `vulkan` feature refuses `infer --backend vulkan` with E-TARGET-001 before the file is read.

For a `muon` file, `ir --stage training` prints the header `optimizer muon lr = … momentum = … weight_decay = … ns_steps = … warmup_steps = … adam_lr = … beta1 = … beta2 = … eps = …`. Each `output %<n> update @<path>` line ends in ` muon` or ` adamw`, the update that the split of § 2.1 gave the parameter. The Newton–Schulz subgraph of a Muon parameter is printed in full, one line per rounded op:
- the momentum update and the Nesterov step;
- the Frobenius normalization;
- a `Transpose` when `rows > cols`;
- `ns_steps` blocks, each one `Transpose`, three `MatMul`s, three scalar `Mul`s and two `Add`s;
- the transpose back;
- the scaled and decayed update.

The shared scalars (`momentum`, `1e-7`, the three coefficients and `weight_decay`) and the host input `optimizer.muon_lr_t` come first. The AdamW constants and the host inputs `optimizer.lr_t`, `optimizer.c1` and `optimizer.c2` appear only if some parameter takes AdamW. `train --backend cpu` of a Muon file prints the same lines as an AdamW run. `--checkpoint` or `--resume` with it is a usage error of one line, exit 2, except `--checkpoint` on a run of `--steps 0` without `--checkpoint-every` as for AdamW (§ 6), and `--backend vulkan` answers E-TARGET-011, exit 1, because `muon` has no Vulkan kernel yet.

`compile <file> --backend cpu|vulkan --output <dir> [--device-profile <json>] [--fast-math]` writes the artifact directory of § 7.1, reads it back through the artifact reader and prints `artifact <artifact_id> <artifact_hash> kernels=<n> <dir>`. A Vulkan compile builds its modules for the `DeviceProfile` JSON file `--device-profile` names (the form `inspect-device --format json` prints) or, without it, for device 0 of the loader, so a missing loader exits 1 with E-TARGET-002 and a compile with a profile opens no loader. With `--device-profile` the plan is also scheduled within the profile's workgroup invocations and workgroup memory, which the manifest records as `matmul_limits`, and the artifact is read back for that profile (§ 5.2, § 7.1); without it the plan is the one for every device. The profile is negotiated before anything is written: a profile below Vulkan 1.2 exits 1 with E-TARGET-004 and the output directory is not created, a profile that reports fewer than 128 workgroup invocations or 16,384 bytes of workgroup memory, the Vulkan minimum the smallest matmul tile needs, exits 1 with E-ARTIFACT-005 naming the field, its bound and the reported value, and no directory is created either, and a profile file that cannot be read or breaks an invariant of `spec/domains/device.yaml` exits 1 naming the file and the invariant. A Cpu artifact has no `kernels/` and its compile opens no loader; `--device-profile` with `--backend cpu` is a usage error. The Cpu and Vulkan artifacts of one file have equal schema hashes and parameters. `compile` replaces the `--emit-spv` of earlier drafts: `spirv-dis kernels/<id>.spv` shows a module. ADR-008 (accepted) adds `--fast-math` to `compile` and to `train --backend vulkan`, which sets the `fast_math` field of the manifest and of every kernel cache key, `false` without it, and so changes the artifact hash; the reader refuses a kernel cache key whose `fast_math` is not the manifest's with E-ARTIFACT-003. The kernels of such an artifact are the ones without the flag less every `NoContraction` decoration, and nothing else in them changes; the `numerics class` line of `--stats` of such a run prints `tolerance`. `--fast-math` with `--backend cpu` is a usage error on both commands. Print readable tensor/training/kernel IR with stable IDs to make optimization decisions debuggable.

## 9. Test and benchmark strategy

**Correctness gates (run before optimizing):**

1. Parser round-trip tests and negative shape/type tests.
2. CPU golden values for each tensor op (including non-square matmuls, transpose and reductions).
3. Finite-difference gradient checks for individual operations and complete linear/MLP graphs; check shared-use adjoint accumulation.
4. Train synthetic linear regression from fixed seeds; verify loss decreases and parameters approach a known solution.
5. Vulkan vs CPU forward, gradients, and post-SGD parameters within documented tolerances over many dimensions, including edges not aligned to workgroup/tile sizes. A device element `g` passes against the CPU interpreter's `c` when `|g - c| <= GPU_ATOL + GPU_RTOL * r`, with `GPU_ATOL = 1e-5` and `GPU_RTOL = 1e-4`; elementwise, broadcast, SGD and transpose kernels use `r = |c|`; for a reduction, loss-sum or matmul element `r` is the sum of the absolute values of its terms (the elements of a `sum`, the `K` products of a matmul element), divided by the element count for `mean` and for `mse` over its squared differences (story:m1-vulkan-reduce-matmul). After a run every parameter passes `||g - c||_2 <= 1e-4 * ||c||_2`, and a bit-for-bit result also passes the tolerance (§ 5.4 item 3). The tests name the tolerance per operator, and each per-kernel case (one kernel per command buffer, not the chained add, relu and SGD case) also checks that the 16 guard words after its output stay unchanged; an SGD update's gradient carries guard words too, so a read past its end changes the parameter's guard words. On a device that does not report denorm preservation for f32 (`shaderDenormPreserveFloat32` false or not reported) the reference `c` is the CPU interpreter run on the inputs with every subnormal flushed to a zero of its sign. A training run on the device, `train --backend vulkan` with its dropout, AdamW and `cross_entropy` steps, is compared with the CPU run of the same file, seed and data by the run tolerance: each step's loss, each held-out loss and each element of every parameter after the run passes when `|g - c| <= GPU_RUN_ATOL + GPU_RUN_RTOL * |c|`, with `GPU_RUN_ATOL = 1e-4` and `GPU_RUN_RTOL = 1e-3`, ten times the kernel tolerance because the per-kernel differences of `exp`, `ln`, the square root and the division compound over the steps; a held-out accuracy over `M` selected rows (the rows of positive weight of every held-out batch) passes when `|g - c| <= 1 / M`, one row whose first largest logit moves to another class. A parameter whose exact gradient is zero by the model's structure, an attention key bias (a parameter read only as the bias of an `add_rows` whose only reader is the key operand of an `attention`: softmax ignores the constant `q · b` it adds to every score of a query, § 2, revision 0.43), receives only rounding noise as its gradient, which AdamW normalises into updates of order `lr · g / (sqrt(v) + eps)` whose sign is the noise's, so the two runs drift apart there by up to about `steps · lr · 1e-3`; each element of such a parameter passes when `|g - c| <= GPU_RUN_ATOL + steps · lr · 1e-3`, `steps` the run's steps and `lr` the optimizer's base rate, and every other parameter keeps the element rule (coordinator decision D74; on the RTX 3090 the twin's other parameters stay at or under 0.009 of their bound through 800 steps). The kernel tolerance still holds for each kernel compared alone (`tests/common/mod.rs`, `GPU_RUN_ATOL` and `GPU_RUN_RTOL` beside `GPU_ATOL` and `GPU_RTOL`; story:bert-vulkan-kernels-attention-loss-adamw).
6. Run `spirv-val` against each generated module in CI; run validation layers during GPU integration tests.
7. Save/load checkpoint mid-training; verify uninterrupted and resumed **CPU** run equivalence under fixed settings, and GPU run equivalence within defined tolerances.
8. Test invalid/oversized model artifacts, zero dimensions, buffer overflows, kernel bounds, device loss, and out-of-memory errors.

**Performance metrics:** steady-state examples/sec and tokens/sec (where relevant), step latency, per-kernel GPU time, number of dispatches, peak allocated VRAM, host↔device transferred bytes, optimizer overhead, and compile time. Distinguish warm-up/shader-pipeline creation from steady-state training. Use fair baselines with the same shapes, dtype, batch, model semantics, and data transfer accounting.

Initial performance goals are **measured correctness and transparent baselines**, not a blanket speedup target. First get within a useful multiple of comparable GPU libraries for large matmul; then compete by specializing common whole-graph patterns, reducing launch overhead and intermediate memory traffic. One target is gated: ADR-007 sets 10× PyTorch eager throughput on the MNIST benchmark example on the RTX 3090, under its timing rule.

### M1 acceptance criteria (unambiguous)

- [ ] A `.mspec` file defines a linear model or MLP, loss, and SGD without Python.
- [ ] Rust compiler parses, checks, builds typed IR, generates gradients and optimizer step.
- [ ] CPU reference backend trains and validates gradients.
- [ ] Runtime finds RTX 3090 through Vulkan and prints verified device features.
- [ ] Compiler emits valid SPIR-V for f32 elementwise, reduction, transpose, matmul and update kernels.
- [ ] Forward, backward, parameter update execute on GPU without CUDA API or toolkit usage.
- [ ] GPU/CPU results are numerically consistent within specified tolerances.
- [ ] Checkpoint save/load and inference work with the same parameter identities.
- [ ] Built kernels, IR, dispatch graph, and performance timings are inspectable.

## 10. Risks and design mitigations

| Risk | Mitigation |
| --- | --- |
| Vulkan backend slower than optimized CUDA libraries | Keep backend abstract; benchmark kernel families separately; optimize tiling, layouts and specialization; do not promise universal superiority. |
| GPU extensions/dtypes vary by driver | Query Vulkan capabilities; have a guaranteed f32 fallback; test actual device, not product assumptions. |
| Poor gradients or numerical instability | Build CPU oracle and finite-difference tests first; use documented f32 reduction and optimizer rules. |
| Autodiff memory explosion | Liveness-aware reuse in M2; explicit checkpoint/recompute planning in M4; memory budget failures are visible. |
| Fusion makes kernels slower | Partition using estimated registers/shared memory and profile results; retain non-fused candidates. |
| Very large specs cause compilation explosion | Bound graph size/dim specialization, intern constants, memoize lowering, expose compilation limits. |
| Driver-specific performance regressions | Cache/re-tune by device and driver identity; keep non-specialized fallback. |
| Unsafe low-level GPU code | Isolate unsafe Rust `ash` calls; static checks, validation layers, bounded address calculation and descriptor ranges. |
| Specification semantics drift with optimizer passes | Version language/IR/operator gradient rules; IR verification and cross-backend differential tests. |

## 11. Execution plan / recommended order

**Iteration 1 — language + CPU (approximately 2–6 focused weeks).** Build the lexer/parser, static `Tensor` types and shape checker, typed SSA graph, interpreter, reverse AD, plain SGD, CLI `check/ir/train --backend cpu`. Train linear regression. This is the first full vertical slice.

**Iteration 2 — GPU bring-up (additional weeks to months).** Create a headless Rust `ash` runtime, probe hardware, upload/download f32 buffers, hand-emit a minimal SPIR-V compute kernel via `rspirv`, verify vector add/relu. Add reduction, transpose and naïve matmul; execute generated training step with explicit synchronization. This is the first non-CUDA RTX 3090 trainer.

**Iteration 3 — architecture and optimizations (months).** Elaboration for modules/layers/generics, optimizer IR, liveness and scratch reuse, fusion, tiled matmul, diagnostics, SPIR-V printing, benchmark harness and on-disk kernel cache.

**Iteration 4 — Transformer path (later).** FP16/capability checks, AdamW, softmax/layer norm, embedding lookup, attention, causal and bidirectional masking, GELU, a masked-language-model head for a small BERT-like proof model beside the GPT-like one, mixed precision, numerical loss-handling and cooperative-matrix specialization if the Vulkan driver exposes it. The BERT-like proof model is BERT-tiny, `examples/bert_tiny.mspec` (two encoder layers of hidden size 128 over the 8,192-token vocabulary of the corpus tokenizer, 1,486,720 parameters, where Turc et al.'s BERT-tiny has 4.4M at 30,522 tokens, written out in the M0 subset without modules), and its hidden-32 twin `crates/modelspec-cli/tests/fixtures/bert_cpu.mspec`, the same program whose every parameter is checked against central differences in `f64` (§ 9 gate 3) and which trains reproducibly on the CPU reference. Both differ from Devlin et al. 2019 in four settings: weight decay applies to every parameter, every matrix is initialised xavier-uniform rather than from N(0, 0.02) and there is no dropout on the attention probabilities, because the language has no parameter groups, no normal initializer and no attention dropout yet, and the warm-up is 10 % of the run rather than 1 % (coordinator decision D70).

If the architecture meets its tests, aggressive per-model specialization and autotuning can follow without changing the public specification format.

## 12. Open design questions (tracked, not blockers for M0)

- **DSL evolution:** keep the canonical source language and versioned AST stable while introducing modules, compile-time loops, and richer control flow.
- **User-defined gradients:** add `vjp` / `jvp` declarations for primitives with nontrivial differentiation; forbid unsound overrides by default.
- **Low-level escape hatch:** later offer a verified kernel specification language instead of injecting opaque arbitrary shaders into Tensor IR.
- **Dynamic tensor dimensions:** choose recompilation/specialization first, bounded runtime dimensions second.
- **Precision contract:** define permitted reassociation, accumulation types, rounding and overflow for f16/f32 combinations, per op.
- **Data interface:** design a compact stream/batch format that does not smuggle Python-style runtime semantics into the compiler. Answered for masked-language-model training (revision 0.45): the packed little-endian `i32` token files and `binding.json` of `modelspec data pack`, whose batch tensors bind to `train` declarations by name, every batch a pure function of the packed data, the masking policy, the run seed and the step (§ 8). A format for other models, held-out evaluation and `infer --input` stay open. Answered for scoring a dense directory (revision 0.60): `infer --data <dir> --function <name> --out <path>` binds the dense files of § 8 to the arguments of any model function and writes its results as an `InferenceOutputFile`, one `f32` row per sample, the layout a dense file reads back with; packed directories as `infer --data` and streaming output stay open.
- **Autotune storage:** cache performance findings with device/driver versioning; never treat cached timings as universal.
- **Second target:** an optional NVIDIA PTX backend could improve performance using NVIDIA's driver interface, but would no longer satisfy the strict **no CUDA API** requirement for that backend. It must remain optional and never contaminate the source language or core IR.

### Architecture decision records

- **ADR-001 — Rust as implementation language:** accepted. Strong typed ownership model for compiler and low-level runtime; no Python dependency.
- **ADR-002 — Vulkan/SPIR-V as initial GPU backend:** accepted. Independence from CUDA APIs is prioritized over immediate peak throughput.
- **ADR-003 — Explicit typed tensor SSA:** accepted. Required for whole-graph analysis, reverse-mode AD, and optimization.
- **ADR-004 — CPU oracle before GPU performance:** accepted. Preserve independent correctness reference.
- **ADR-005 — Whole training-step compilation:** accepted. Optimizer updates and side-effect ordering are part of compilable IR.
- **ADR-006 — No direct SASS:** accepted for v1. Native instruction compilation remains the vendor driver's responsibility.
- **ADR-007 — 10× PyTorch eager throughput on the MNIST benchmark example:** proposed. On the MNIST benchmark example (784 → 64 ReLU → 10, no bias, `f32`, MSE, SGD lr 0.1, batch 100, 3 epochs, 1,800 steps), ModelSpec on the RTX 3090 trains at least 10× as many images per second as PyTorch eager on the same host and device, with the same test accuracy and final weights within the tolerance of § 9 gate 5, and bit for bit where § 5.4 says so.
  - Baseline: PyTorch `2.14.1+cu130`, eager, on an NVIDIA GeForce RTX 3090 with driver 610.57.04, with `torch.use_deterministic_algorithms(True)`, TF32 off, `set_float32_matmul_precision("highest")`, the host thread pinned to one CPU, and the same data, initialization and shuffle order. Measured on 2026-10-21 (planning store, `verification-report:mnist-benchmark-cuda-baseline`): 519 µs per step, 192,741 images/s, test accuracy 0.9088. The gate is 1,927,410 images/s, 51.9 µs per step. `torch.compile` (933 µs per step) is reported beside it, not gated.
  - Timing rule: the training loop including minibatch gather and one-hot creation, and for ModelSpec command recording, submission and the wait for the last step; excluding loading (the data set upload of § 6.3 included), compilation and pipeline creation, a 20-step warmup, evaluation and IO. Three repeats, the median. ModelSpec runs with `deterministic` on and `fast_math` off (§ 3.3).
  - Working target: 31.4 µs per step. PyTorch eager on the same host's CPU is fastest at 8 threads, 314 µs per step median (planning store, `verification-report:pytorch-cpu-multithread-2026-10-22`, measured on 2026-10-22 under load, so an upper bound on the quiet time), faster than PyTorch eager on CUDA. 10× over the fastest PyTorch eager figure on this host is 31.4 µs per step, below the 51.9 µs gate above; the work aims at 31.4 and the gate stays 51.9.
  - GPU timing method: the RTX 3090 idles at P8 and a run under one second stays at P3 (780 MHz of 2130 MHz), so a figure from a cold device measures the clock floor, not the schedule. Before the timed window the device runs the same program for at least 5 s; the timed window is at least 5 runs of at least 5 s each, back to back; `nvidia-smi --query-gpu=timestamp,clocks.sm,pstate` samples every 200 ms throughout. The report gives the median and the range of the per-run steady-state µs per step and the share of samples per performance state with its mean SM clock during the window. Clocks are not locked. No other compute process is on the device.
  - Relation to ADR-002: the independence from CUDA APIs stays, and the PyTorch side of the benchmark runs outside the repository. ADR-002's priority of independence over throughput stays for every other model; for this example throughput is a gated target. The design is § 6.3, its per-step budget the table there.
- **ADR-008 — Opt-in fast-math mode:** accepted (2026-10-24). `fast_math = true` (§ 3.3) lets a Vulkan artifact trade which bits it produces for throughput, never whether two runs agree: a `fast_math` artifact gives the same bits on every run on one device and driver, and its results are compared within tolerance, never bit for bit.
  - Permitted: the driver may contract an `OpFMul` and an `OpFAdd` into a fused multiply-add, because the kernels no longer decorate them with `NoContraction`, which today every `OpFAdd`, `OpFSub` and `OpFMul` of a reduction, loss-sum or matmul module carries (`crates/modelspec-runtime/src/spirv/emit.rs:603`, `:900-920`). A matmul may run as a cooperative-matrix kernel where the device reports `VK_KHR_cooperative_matrix` (§ 5.2, M4). The `mse` loss sum may spread over many workgroups instead of the one it runs in now (`crates/modelspec-core/src/schedule.rs:456`), in two stages whose order the shape alone fixes, as for the two-stage reductions of § 5.2.
  - Not permitted: `deterministic` keeps its meaning (§ 3.3). There is no split-K, no reassociation beyond that fixed two-stage order, and no TF32 or other reduced-precision accumulation; every sum accumulates in `f32`.
  - Comparison: a `fast_math` run passes against the CPU oracle within the tolerances of § 9 gate 5, `GPU_ATOL = 1e-5`, `GPU_RTOL = 1e-4` and the whole-run L2 bound of `1e-4`, unchanged (§ 5.4 item 2). The run record and the `numerics class` line of `--stats` name the class `tolerance`. Nothing claims a bit-for-bit result for a `fast_math` artifact.
  - Benchmarks: ADR-007's figures are measured with `fast_math` off. A `fast_math` figure may be reported beside the deterministic figure, labelled as such, never as the headline.
- **ADR-009 — Deterministic kernels use an explicit fused multiply-add:** accepted, implemented by story:deterministic-fma in commit a32cb64 (2026-10-24, coordinator under Timo's grant of 2026-10-24: "You have all authority now to make these decissions yourself. also, "later" is now :) - its your project and you can make it a success. Take decissions by yourself!"). In `deterministic` mode the first product of a matmul, reduction or loss-sum element is a plain `OpFMul` (so a signed zero survives) and every later product is fused into the running sum by one IEEE 754 fused multiply-add (`OpExtInst GLSL.std.450 Fma`, rounded once), and the CPU oracle computes the same element with `f32::mul_add` in the same order (§ 3.3). `NoContraction` stays on every `OpFAdd`, `OpFSub` and `OpFMul` that remains, so the driver neither fuses nor splits anything; the fused operation is explicit, and its single rounding on a device is established by `vulkan_fma_oracle` on that device, never assumed (§ 5.4 item 1), so the bit-for-bit class of § 3.3 keeps its meaning across runs on a device that passes it.
  - Why: under `NoContraction` a product and its sum are two instructions, and the FP32 ceiling of the GA102 is half of its fused peak (10,496 lanes × 1 instruction per clock, about 17.8 TFLOP/s at 1.7 GHz, inferred from the published lane count). The forward matmul `[8192, 784] x [784, 4096]` of `mlp_sweep` b8192 h4096 runs at 9.2 TFLOP/s deterministic and 11.4 under `fast_math` (`benchmarks/raw/2026-10-24-tile256/padonly-*`); beating PyTorch eager CUDA at that size (7,290.5 µs, 14.7 TFLOP/s effective over the step) needs about 19 TFLOP/s on the two large sites, above the unfused ceiling.
  - Cost: the bits of every matmul, reduction and loss output change once. The goldens, the plan-site digests (`crates/modelspec-runtime/tests/fixtures/matmul_plan_sites_same_bits.txt`), the recorded `train` stdout hashes and every checkpoint fixture are re-recorded in the unit that lands it, with the CPU oracle changed in the same commit, so CPU and Vulkan agree bit for bit before and after. The artifact hash changes with the kernels. A run record names the compiler version, so a result from before the change is attributable.
  - Not changed: one invocation per output element, ascending `k` from the `k = 0` product, no split-K, the fixed two-stage loss order; `fast_math` keeps ADR-008's meaning (the driver may contract what the kernel leaves unfused; with ADR-009 nothing of a matmul's inner loop is left to contract, so the `fast_math` gain moves to cooperative matrices and the loss sum).
  - Relation to ADR-004: the CPU oracle stays the reference; `mul_add` on x86-64 with FMA3 (and `fma` on aarch64) is the same IEEE operation the GPU performs. A CPU without an FMA instruction computes `mul_add` in software, slower and bit-equal.
- **ADR-008 amendment (2026-10-24, coordinator under the same grant):** under `fast_math`, a cooperative-matrix matmul may take `f16` or `bf16` operands with `f32` accumulation where the device reports such a shape (`VK_KHR_cooperative_matrix`; the RTX 3090 reports `FLOAT16` and `BFLOAT16` operands with `FLOAT32` accumulator and result, and no `f32`-operand shape, `inspect-device`, decision-blocker:cooperative-matrix-f32-operands). Every sum still accumulates in `f32`; no split-K; the run record and `--stats` name the numerics class `tolerance` and the operand type. Comparison: within the tolerances of § 9 gate 5 against the CPU oracle computing with the same rounded operands (the oracle rounds its inputs to the operand type before the product). Benchmarks: a reduced-precision-operand figure is compared only against a PyTorch baseline of the same operand precision (`torch.autocast` to the same dtype, TF32 off elsewhere), labelled, never against the FP32 TF32-off baseline of ADR-007 and never as the headline; the deterministic figure stays the headline. The ADR's "no TF32 or other reduced-precision accumulation" stands: operands may be reduced, accumulation may not.
  - Why now: at batch 8192 and hidden 4096, 107,239,964,672 FLOP per step, ModelSpec 0.6.0 on the RTX 3090 reaches 3.452 TFLOP/s (31,067 µs per step) against 14.710 TFLOP/s (7,290 µs) for PyTorch eager on CUDA (`benchmarks/runs.yaml`, runs `sweep-b8192-h4096-modelspec-vulkan` and `sweep-b8192-h4096-pytorch-cuda-eager`). `NoContraction` forbids the fused multiply-add that the device's peak throughput assumes.
  - Status: accepted by the operator on 2026-10-24. `story:fast-math-mode` in the planning store implements it and depends on `story:matmul-shape-aware-tiling`, so deterministic tiling comes first.
