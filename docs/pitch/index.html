ModelSpec

Specify what the model computes.
The compiler decides how it runs.

A declarative language and a Rust compiler for differentiable tensor programs. One .mspec file is the whole training step.

Rust Vulkan compute + SPIR-V first target: RTX 3090 no Python · PyTorch · CUDA
Vision objective; DESIGN.md header principle and section 0. Date and version: the 0.13.0 release, 2026-10-25 (CHANGELOG.md § 0.13.0).

The problem

A training run today is a Python program over a framework, a CUDA toolkit and a driver.

01

What ran is scattered

Shapes, gradient graph, optimizer state and random streams live in runtime objects. Nobody can read them back as one artifact.

02

Errors arrive late

Shape and dtype errors surface at run time, often after GPU time has been spent.

03

Reproducing means rebuilding

To reproduce a run you reproduce an environment, not re-read a file.

04

No target for model writers

A person, script or agent that edits models has no small, typed target to check before it runs.

Vision, "The problem".

One file is the whole training step

model LinearReg {
    param w: Tensor<f32, [4, 1]> = xavier_uniform();

    fn forward(x: Tensor<f32, [8, 4]>)
        -> Tensor<f32, [8, 1]> {
        return matmul(x, w);
    }
}

train Fit {
    model = LinearReg;
    input  x: Tensor<f32, [8, 4]>;
    target y: Tensor<f32, [8, 1]>;
    loss = mse(model.forward(x), y);
    optimizer = sgd(lr = 0.1);
    steps = 500;
    seed = 42;
    device = cpu;
}
  • model: parameters and a pure forward
  • train: loss, optimizer, data bindings, execution policy
  • Every shape is in the type; a mismatch is a compile error
  • No backward pass is written: the compiler derives it
  • Source + seed determine the run
README example, identical to examples/linear_regression.mspec. Vision "What ModelSpec is".

The pipeline

DESIGN.md section 3 and 3.1. Parse and name resolution happen before the checked HIR. The driver translates SPIR-V into native GPU code; ModelSpec does not emit SASS (section 0, 5.1). Legend: M0 released as 0.1.0 (CHANGELOG.md § 0.1.0); train --backend vulkan first released in 0.4.0 (CHANGELOG.md § 0.4.0).

Seven invariants, non-negotiable

1One semantic coreCPU and GPU consume the same verified tensor IR
2Composition is not a kernel boundaryLayers are inlined; operations may fuse or split
3Shapes and dtypes are explicitInvalid operations are rejected before dispatch
4Pure by defaultParameters, randomness and updates have explicit identities and effects
5Training is compiledForward, loss, backward, optimizer: one train_step
6Hardware features are queriedNo assumed extension, dtype or matrix shape
7Testable at every lowering stageIntrospection, differential tests, profiling

And a priority, not an invariant: correctness before speed. Near-optimal performance is a long-term goal, not a v1 guarantee.

DESIGN.md section 0. A change that breaks one is refused (AGENTS.md).

What you get

  • A diff you can review
    Architecture, loss and optimizer change in one file
  • Errors before compute
    Coded diagnostics with source spans
  • Runs you can repeat
    Init from Philox4x32-10, keyed by seed and a blake3 hash of each parameter path
  • A reference for every GPU result
    The CPU oracle runs the same IR
  • Every stage inspectable

Use cases

01

Reviewable model changes

A model change is a .mspec diff. modelspec check refuses a shape or type error before training starts.

02

Reproducible experiments

Same source and seed, same run. Checkpoints carry a blake3 checksum.

03

Differential GPU testing

Every kernel, fusion and pass is checked against the CPU interpreter on the same IR.

04

Training without Python

MLPs on a consumer GPU through Vulkan; small GPT-like models from M3.

Direction · not a planned milestone

Self-improvement, part 1

01

Agents propose models as spec diffs

An agent edits a .mspec file. The checker rejects an invalid proposal in milliseconds.

Only checked proposals reach training.

02

A compiler that improves its own kernels

Agents propose passes, fusions and kernel variants. Accepted only if differential tests against the CPU oracle stay green and a benchmark improves.

Speed can change. Semantics cannot change unseen.

Vision direction items 1 and 2.
Direction · not a planned milestone

Self-improvement, part 2

03

Self-tuning training recipes

Optimizer, schedule and initialization are part of the spec. A search loop changes them as data.

Every run, its source and its seed are recorded as evidence.

04

Models that write ModelSpec

A model trained by ModelSpec generates and repairs .mspec programs. The small, typed language makes its output checkable.

model → trainer → model

Vision direction items 3 and 4.
Direction · not a planned milestone

Guardrails: what stays human

A human decision, always

  • Changing an invariant
  • Starting a device run
  • Widening what the loop may change

Every proposed improvement goes through the process ModelSpec is built with:

story → implementor → adversarial review → gate → recorded evidence

Non-goal: autonomous self-modification without review.

Vision direction item 5 and "Non-goals".
