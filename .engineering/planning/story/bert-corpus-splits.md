# Prepare a public text corpus into train and held-out splits in Rust

## Context

`epic:bert-from-scratch` (Outcome: "a small public corpus"; In scope, Evaluation: "MLM loss and
accuracy on a held-out split"). No corpus is named by the epic or by any file in the repository,
so the choice is the open question of the marker below. `spec/domains/data.yaml` types the corpus
as `modelspec.data.Dataset` with `splits` of `modelspec.data.DatasetSplit`, one per
`modelspec.data.SplitRole` (`Train`, `HeldOut`). The pipeline is Rust (the summary of
`spec/domains/data.yaml`; AGENTS.md: no Python), in a new module of `modelspec-runtime`, which has no
Vulkan dependency outside its `vulkan` feature.

This is the first of three data stories: corpus and splits, then `story:bert-tokenizer`, then
`story:bert-mlm-batches`. `story:bert-train-data-binding` connects them to `modelspec train`.

## Open questions settled first

Two `UNMAPPED:` markers of `spec/domains/data.yaml` stand in front of this story, named by where
they sit and a quoted fragment of their text, never by line number. Each is settled before any
code, in that file, with `ess specify validate --path .` in `spec/` passing afterwards. A
settlement names its source (the operator, DESIGN.md or another ESS document); where none answers,
the story stops at that step and reports the question instead of choosing.

1. Marker on `modelspec.data.Dataset`, text "which public corpus, and whether a dataset holds raw
   text": which public corpus (its name, its licence, the exact release and how the operator obtains
   it), and whether a `Dataset` holds raw text or token sequences packed by one tokenizer. If it
   holds packed sequences, the settlement also declares the relation to `modelspec.data.Tokenizer`
   and its ownership, and a type for the raw-text splits this story writes; `story:bert-mlm-batches`
   then writes the `Dataset` record.
2. Marker on `modelspec.data.DatasetSplit`, text "how a split is made and identified": how a split
   is made (the split files of the corpus release, a deterministic fraction, a content hash) and
   what identifies it; the fields of `DatasetSplit` follow.

## What this story decides

- `modelspec data prepare <corpus> --out <dir>` reads the settled corpus from local files (no
  network access) and writes the splits and a JSON record of them into `<dir>`. Running it twice on
  the same input writes byte-identical files: identifiers are derived from content (a UUID made
  from the leading bytes of a `blake3` hash), not drawn at random.
- The JSON Schema of every record this story writes is generated by `ess generate --kind schema`
  into `crates/modelspec-runtime/schema/`, outside `spec/` (AGENTS.md), and joins the schema drift
  check `task ci` runs (added by `story:observatory-live-event-stream`).
- An unreadable corpus or output directory prints `modelspec data prepare <path>: <error>` and exits
  1 with no diagnostic code, as `modelspec check` does for an unreadable file (inferred from
  `crates/modelspec-cli/src/check.rs:22-27`); a usage error exits 2 (AGENTS.md exit codes).
- Tests use a corpus fixture written for this story, a few short documents of original text, so
  `task ci` needs neither the corpus nor network access.

## Order on shared files

This story edits `crates/modelspec-cli/src/lib.rs` (the `data` subcommand), `Taskfile.yml` (the
drift check), `AGENTS.md` (Commands and State), `crates/modelspec-runtime/Cargo.toml`, `Cargo.lock`
and `website/docs/reference/cli.md`. The observatory stories edit the first five
(`story:observatory-live-event-stream`, `story:observatory-run-recording-replay`,
`story:observatory-ui-live-loss-chart`), and I do not know whether a later one adds a dependency,
so this story depends on `story:observatory-saliency-gradient-x-input`, the last of that chain. It
runs beside the operator stories from `story:bert-embedding-lookup` to `story:bert-adamw-warmup`,
which edit none of these files and add no dependency; `story:bert-tokenizer` follows it.

## Domain relations

- `modelspec.data.Dataset` holds its `splits` as a field `List<modelspec.data.DatasetSplit>` with
  the invariant `distinct: {in: splits, as: split, by: split.role}` (`spec/domains/data.yaml`): one
  split per role, each part of the dataset value and gone with it.
- The relation of a `Dataset` to a `Tokenizer` is not declared (the marker on `Dataset`); this story
  declares it only if the first settlement says a dataset holds packed sequences.

## Acceptance

`modelspec data prepare` turns the fixture corpus into exactly one `Train` and one `HeldOut` split,
reproducibly, and writes a record that validates against the generated schema.

Scenarios, each run by `task ci` through the command shown, except scenarios 1 and 5:

1. `spec/domains/data.yaml` no longer contains the markers on `Dataset` ("which public corpus") and
   on `DatasetSplit` ("how a split is made and identified"); typed declarations that cite their
   source stand in their place, and `cd spec && ess specify validate --path .` exits 0.
2. `cargo test -p modelspec-cli --test data_prepare splits`: on the fixture corpus, the record
   names exactly one split per role, every fixture document is in exactly one split, and the record
   validates against the schema in `crates/modelspec-runtime/schema/`.
3. `cargo test -p modelspec-cli --test data_prepare reproducible`: two runs into two directories
   write byte-identical files.
4. `cargo test -p modelspec-cli --test data_prepare refusals`: a missing corpus path exits 1 with a
   message naming it; no `--out` exits 2.
5. Planted drift, run by hand once before the story is done, its output kept as evidence: with
   the first entry of the `required` list deleted from the committed JSON Schema of the record
   `modelspec data prepare` writes, in `crates/modelspec-runtime/schema/`, `task ci` exits non-zero
   at its schema drift check and the output names that file; with the file restored, `task ci`
   exits 0. `grep -q crates/modelspec-runtime/schema Taskfile.yml` exits 0.
6. `task docs-check` exits 0, and `website/docs/reference/cli.md` lists `data prepare`.
